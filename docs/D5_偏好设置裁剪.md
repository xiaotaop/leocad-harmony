POV-Ray、LGEO、外部零件库路径，渲染页仍有 Blender 设置。

## 1. 为什么现在才修

D4 的交付是「主窗口去除非本期菜单」，我摘掉了菜单里的命令，但没有处理**配置这些
功能的控件**。组长的判断是对的：

> 不能把菜单无 Import/Export 等同于全部设置已裁剪。

菜单移除挡住的是「怎么进去」，偏好设置挡住的是「进去以后改什么」。两者是不同层，
D4 只做了前一层。

## 2. 方案：隐藏控件，不改 `.ui`

D2 §6.4 已经定了：

> 按 D1 §3.1 第 5 条原则，**不改 `.ui`**，用隐藏控件实现。

沿用这个决定，理由仍然成立：

- 上游 `.ui` 保持原样，后续同步上游时不会冲突；
- 控件名不变，读这些控件的代码（`accept()` 里逐项读回）不用动；
- 与文件里既有的 `#if defined(Q_OS_WIN) || defined(Q_OS_MACOS)` 隐藏 `povray*` 是同一
  种做法，不是新发明。

## 3. 隐藏了什么

| 页面 | 控件 | 为什么 |
|---|---|---|
| 常规 | `checkForUpdates` + `label_10` | 菜单项已移除，这项只配置一个跑不起来的功能 |
| 常规 | `partsLibrary` / `partsLibraryBrowse` / `partsArchiveBrowse` + `label_5` | 首发完全离线，库编译进包内；用户改路径正是启动横幅无法描述的那种情况（见 `lcPiecesLibrary::IsLibraryDegraded()`） |
| 常规 | `povrayExecutable` / `povrayExecutableBrowse` + `povrayLabel` | 首发不做外部渲染 |
| 常规 | `lgeoPath` / `lgeoPathBrowse` + `label_9` | 同上，LGEO 是 POV-Ray 的配件库 |
| 渲染 | `BlenderAddonSettingsButton` + `label_39` | 首发不做 Blender 集成 |

### 3.1 一个差点踩进去的坑

`CustomPathsGroup` 这个分组框里同时装着：

- 零件库路径、POV-Ray、LGEO（**要隐藏**）
- 颜色配置文件、人仔设置文件（**要保留**）

第一版我按组隐藏，会把后两项一起带走。这两个都是应用启动时要读的本地文件，
D2 §6.4 的保留清单里有。改成逐个控件隐藏。

**标题跟着字段走**：只隐藏字段不隐藏标题，标题会变成它下面那一行的标签。比如
「Parts Library:」下面接着「Color Configuration:」，读起来像是颜色配置的说明。
所以每对都是成对隐藏。

## 4. 代码结构：一份清单，两处使用

隐藏名单放在 `lcPreferencesDialog::ScopedWidgets::Hidden()`，`ApplyFirstReleasePreferencesScope()`
遍历它调用 `hide()`；测试读同一份名单。这样「代码隐藏了什么」和「测试断言隐藏了什么」
不可能分叉。

另有一份 `Kept()` 名单，只给测试用，列出必须保留的控件。它不是对称设计，是刻意的：
对话框只按名字隐藏，从不枚举其余控件；测试需要显式清单，否则「保留」是空话。

`Q_ASSERT_X` 在找不到控件时触发：`.ui` 里改名会让 `hide()` 变成静默空操作，而
`findChild` 返回 null 不会报错。测试里也有 `hiddenWidgetsExistInTheUi` 守这条。

### 5.1 为什么测试不构造对话框

`lcPreferencesDialog` 的构造函数会执行：

```cpp
lcViewWidget* Widget = gMainWindow->GetActiveView()->GetWidget();
QOpenGLContext* Context = Widget->context();
QOpenGLFunctions* Functions = Context->functions();   // ← 空指针
```

离屏平台上 `context()` 返回 null，对话框在构造函数里就段错误。我实测过：建好窗口、
`SetProject` 之后 `GetActiveView()` 非空，但 `GetWidget()->context()` 仍是 null。

**这是上游既有耦合，不是本次改动引入的**，也不该在测试里绕过——绕过的写法会在真机
上给出虚假信心。所以测试改为验证「裁剪名单 vs 真实 `.ui`」，不构造对话框。

代价要说清楚：**这组测试不能证明控件在真机上确实不可见**，只能证明名单正确、名字
存在、保留项没被误伤。真机可见性仍需组长复验（§7 第 1 项）。

### 5.2 回归验证

两个方向都实际改坏过：

| 改坏的行为 | 失败项 | 报错 |
|---|---|---|
| 按组隐藏 `CustomPathsGroup` | 1 | `the external parts library path is still shown` |
| 从保留名单删掉 `ColorConfigEdit` | 1 | `ColorConfigEdit is not kept, but it is a local settings file the app reads` |

第二条是反方向的保护：只测「藏够了」会漏掉「藏多了」。

### 8.1 给 A 的 D4-01 线索

代码路径：

```cpp
// common/lc_view.cpp:800
mRenderImage = QImage(Width, Height, QImage::Format_ARGB32);

// common/lc_view.cpp:833
QImage lcView::GetRenderFramebufferImage() const { return mRenderFramebuffer->toImage(); }

// common/lc_view.cpp:962 —— 裸 memcpy，按 4 字节/像素假设通道顺序
memcpy(dst, src, CurrentTileWidth * 4);
```

`QOpenGLFramebufferObject::toImage()` **不保证**返回 `Format_ARGB32`，格式随平台。
设备日志确认是真 GLES（`is_gles: true`、`OpenGL ES 3.2`），GLES 上通常是
`Format_RGBA8888`，相对 ARGB32 红蓝互换——这与「Red 显示成 Blue」吻合。

但**没有证明**：LightBlue 显示偏黄不是单纯红蓝互换，可能是另一条路径（缩略图管理器
的 `convertToFormat`，或颜色值本身）。建议 A 在真机打印 `toImage()` 的实际
`format()`，再决定修哪里，而不是按线索直接交换通道。

我试过一版修复（在 memcpy 前判断格式并 `convertToFormat(Format_ARGB32)`），
代码已撤回，未提交。
