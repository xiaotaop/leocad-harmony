## 1. 为什么现在才修

D4 的交付是「主窗口去除非本期菜单」，我摘掉了菜单里的命令，但没有处理**配置这些
功能的控件**。组长的判断是对的：

> 不能把菜单无 Import/Export 等同于全部设置已裁剪。

菜单移除挡住的是「怎么进去」，偏好设置挡住的是「进去以后改什么」。两者是不同层，
D4 只做了前一层。

## 2. 方案：隐藏控件，不改 `.ui`

D2 §6.4 已经定了：

> 按 D1 §3.1 第 5 条原则，**不改 `.ui`**，用隐藏控件实现。

沿用这个决定，理由仍然成立：

- 上游 `.ui` 保持原样，后续同步上游时不会冲突；
- 控件名不变，读这些控件的代码（`accept()` 里逐项读回）不用动；
- 与文件里既有的 `#if defined(Q_OS_WIN) || defined(Q_OS_MACOS)` 隐藏 `povray*` 是同一
  种做法，不是新发明。

### 3.1 一个差点踩进去的坑

`CustomPathsGroup` 这个分组框里同时装着：

- 零件库路径、POV-Ray、LGEO（**要隐藏**）
- 颜色配置文件、人仔设置文件（**要保留**）

第一版我按组隐藏，会把后两项一起带走。这两个都是应用启动时要读的本地文件，
D2 §6.4 的保留清单里有。改成逐个控件隐藏。

**标题跟着字段走**：只隐藏字段不隐藏标题，标题会变成它下面那一行的标签。比如
「Parts Library:」下面接着「Color Configuration:」，读起来像是颜色配置的说明。
所以每对都是成对隐藏。

### 3.2 平台分支会删控件，裁剪必须排在它前面（评审 P2 修正）

首次提交里，裁剪函数排在构造函数第 49 行，而 Windows/macOS 分支在第 31 行就
`delete ui->povrayLabel`。裁剪名单里有 `povrayLabel`，`findChild` 返回 null，
`Q_ASSERT_X` 在 Debug 构建里直接中止——**正常打开偏好设置就会失败**。

组长在 Windows x64 / Qt6.12 / offscreen 上用真实 `.ui`、复制的平台清理顺序复现：
进程退出 `-1073740286`；把裁剪调用移到删除之前，同一程序退出 0。

**修复**：把 `ApplyFirstReleasePreferencesScope()` 移到平台清理之前。

顺序不是随手排的，代码注释里写了原因：

```cpp
// Runs BEFORE the platform cleanup below, not after: that block deletes
// ui->povrayLabel on Windows and macOS, and a name the scope list hides would
// then no longer exist.
ApplyFirstReleasePreferencesScope();

#if defined(Q_OS_WIN) || defined(Q_OS_MACOS)
    ...
    delete ui->povrayLabel;
#endif
```

同时把隐藏循环抽成 `HideFirstReleaseWidgets(QWidget* Container)`，返回未能解析的
名字个数：

- 对话框调用它，`Q_ASSERT_X(Missing == 0, ...)` —— 名字写错仍然会在 Debug 下暴露；
- 测试用任意容器调用它，不需要构造对话框（构造函数后面有 GL 查询）。

这样「断言」和「可测试」不冲突：断言留在对话框里，函数本身可以在别的容器上跑。

## 4. 代码结构：一份清单，两处使用

隐藏名单放在 `lcPreferencesDialog::ScopedWidgets::Hidden()`，`ApplyFirstReleasePreferencesScope()`
遍历它调用 `hide()`；测试读同一份名单。这样「代码隐藏了什么」和「测试断言隐藏了什么」
不可能分叉。

另有一份 `Kept()` 名单，只给测试用，列出必须保留的控件。它不是对称设计，是刻意的：
对话框只按名字隐藏，从不枚举其余控件；测试需要显式清单，否则「保留」是空话。

`Q_ASSERT_X` 在找不到控件时触发：`.ui` 里改名会让 `hide()` 变成静默空操作，而
`findChild` 返回 null 不会报错。测试里也有 `hiddenWidgetsExistInTheUi` 守这条。

### 5.0 第一版测试为什么没抓到

首版测试只做两件事：核对隐藏/保留名单，以及从 `.ui` 里读出控件名确认它们存在。
它**从不执行裁剪函数**，也不看真实对象树，所以「构造函数先删了控件、裁剪后才跑」
这个回归它根本碰不到——名单对、名字也在 `.ui` 里，全绿。

组长指出得准确：仅从原始 `.ui` 读取名字，无法检测控件在构造过程中已被删除。

新增的两项补上这个缺口：`scopeActuallyHidesOnARealTree` 在真实控件树上跑真实裁剪
（这是组长建议的「用真实 UI 容器单独执行裁剪，避免依赖构造函数后面的 GL 查询」），
`scopeMustRunBeforeThePlatformCleanup` 把顺序约束钉住。

### 5.1 为什么测试不构造对话框

`lcPreferencesDialog` 的构造函数会执行：

```cpp
lcViewWidget* Widget = gMainWindow->GetActiveView()->GetWidget();
QOpenGLContext* Context = Widget->context();
QOpenGLFunctions* Functions = Context->functions();   // ← 空指针
```

离屏平台上 `context()` 返回 null，对话框在构造函数里就段错误。我实测过：建好窗口、
`SetProject` 之后 `GetActiveView()` 非空，但 `GetWidget()->context()` 仍是 null。

**这是上游既有耦合，不是本次改动引入的**，也不该在测试里绕过——绕过的写法会在真机
上给出虚假信心。所以测试改为验证「裁剪名单 vs 真实 `.ui`」，不构造对话框。

代价要说清楚：**这组测试不能证明控件在真机上确实不可见**，只能证明名单正确、名字
存在、保留项没被误伤。真机可见性仍需组长复验（§7 第 1 项）。

### 5.2 回归验证

两个方向都实际改坏过：

| 改坏的行为 | 失败项 | 报错 |
|---|---|---|
| 按组隐藏 `CustomPathsGroup` | 1 | `the external parts library path is still shown` |

## 7.1 D5-02：切到 System 主题后文字不可见（issue **#33**）

> 关联更正：主题可用性独立跟踪 **#33**；#14 是原偏好裁剪事项，两者不混为一谈。

真机验收发现（成员 C 主责）：深色主题启动 → 偏好设置里把颜色主题改为
System → 重置颜色选 No → OK，主菜单文字与当前颜色名不可见。配置写入 `ColorTheme=1`，
新 PID 重启后仍复现——**设置持久化成功，主题不可用**。

### 根因（**假设，待真机确认**）

> **证据边界先说清楚。** 下面这条链路是从**宿主实验 + 故障形状**推断的，**没有**
> 设备侧证据：原真机记录没有打印 `style()->objectName()`、样式类名、
> `QStyleFactory::keys()` 或 `setStyle()` 的返回值。因此本补丁的性质是
> **防御性修复**，不是「已证实的根因修复」。真机证据由 §7.1.1 的诊断输出补齐。

`lcApplication` 构造时记录默认样式名，`UpdateStyle()` 在非深色分支用它还原：

```cpp
mDefaultStyle = style()->objectName();          // 推测鸿蒙平台插件返回空串
...
QApplication::setStyle(mDefaultStyle);           // setStyle("") 返回 null，样式不变
QApplication::setPalette(qApp->style()->standardPalette());
qApp->setStyleSheet(QString());                  // 深色样式表已被清掉
```

`QApplication::setStyle("")` **返回 null 且不改变当前样式**——这一条有宿主实测
（返回 false，样式仍是 Fusion）。**推断**：鸿蒙上样式名同样为空，于是切到 System 时

1. 样式仍停留在深色主题装的 Fusion；
2. 深色样式表被清空；
3. 调色板换成 `standardPalette()`——取自那个残留样式；

样式与配色不再匹配，表现为菜单与颜色名文字消失。

**已知反例提示**：本机健康路径上 `active_before` 同样是空串（见下），说明
`objectName()` 为空并非鸿蒙独有。因此「名字为空」可能只是必要条件，不是充分条件；
真机上还可能有 `standardPalette()` 本身的问题。这正是本条必须标为假设的原因。

### 7.1.1 诊断输出（供真机取证）

`UpdateStyle()` 现在每次应用主题都输出一行，真机用 `LEOCAD_THEME_STYLE` grep：

```
LEOCAD_THEME_STYLE {"default":"...","active_before":"...","class_before":"..."}
LEOCAD_THEME_STYLE {"fallback":"Fusion","applied":true,"known":[Windows,Fusion]}   ← 仅在还原失败时
LEOCAD_THEME_STYLE {"active_after":"...","class_after":"...","window":"#..."}
```

这三行足以判定：默认名是否为空、还原是否成功、回退是否真的应用、以及最终
`Window` 颜色取自哪个样式。真机复验时请一并回传。

### 真机复验推翻了上述假设（2026-10-31 第二轮）

组长从 `ba36110b` 独立构建 ARM64 签名包（80,068,486 字节，SHA-256
`88039eca…f45716`）真机复验，结果为 **No / Yes 四条路径全部仍不可见**，且新增的
`LEOCAD_THEME_STYLE` 诊断直接否定了假设：

```
{"default":"ohos","active_before":"","class_before":"QStyleSheetStyle"}
{"active_after":"ohos","class_after":"QOhosStyle","window":"#ffffff"}
```

- `default` 是 **`ohos`，非空**——「样式名为空」的假设不成立；
- 保存前的 `active_before: ""` 是 `QStyleSheetStyle` 包装层的属性，不等于
  `mDefaultStyle` 为空；
- 没有 `fallback` 记录、没有 `Could not restore` 警告——**回退分支从未进入**；
- `class_after: QOhosStyle`、`window: #ffffff`——样式与窗口底色都已正确恢复。

**所以真正的问题不是样式还原，而是恢复后的调色板里文字角色不可读。**
`window` 已变白而文字仍看不见，正是「文字色与背景色相同」的形状。

### 修复：不再盲信样式自带的调色板

`QApplication::style()->standardPalette()` 由平台样式提供，**不保证自洽**。
新增 `EnsureReadablePalette()`：以 WCAG 对比度（阈值 3.0，AA 大字号/UI 组件级）
检查三组文字/背景角色，不达标则按背景亮度换成深/浅可读色。

| 文字角色 | 背景角色 | 对应控件 |
|---|---|---|
| `WindowText` | `Window` | 主菜单栏、颜色列表分组名 |
| `Text` | `Base` | 零件面板、列表视图 |
| `ButtonText` | `Button` | 颜色名工具按钮 |

替换色由背景推导（亮背景→`#1e1e1e`，暗背景→`#f0f0f0`），不硬编码黑白，
因为不同平台样式的底色不同。诊断也扩展为打印全部六个角色，真机可直接看出
`windowtext` 是否等于 `window`。

**这一版仍是假设驱动的防御性修复**，但方向已被设备证据约束：不再是猜「样式没恢复」，
而是针对「恢复后的文字角色不可读」这个已被观察到的结果。真机仍需确认。

### 第三轮真机复验：应用级调色板也不是根因（2026-10-31）

组长从 `a439bf20` 构建 ARM64 签名包（80,080,203 字节，SHA-256

**这组数值的对比度是正常的**：`windowtext #182431` 在 `window #ffffff` 上清晰可读，

所以此前两版的判断都被推翻，必须明确记录：

| 版本 | 曾认为的根因 | 真机结论 |

### 设备的调色板本身自相矛盾（可验证的缺陷）

把设备报的六个值摊开看：

| 角色 | 值 | 亮度侧 |
|---|---|---|
| `window` | `#ffffff` | 亮 |
| `base` | `#e4e4e4` | 亮 |
| `button` | `#000000` | **暗** |
| `windowtext` | `#182431` | 暗 |
| `text` | `#182431` | 暗 |
| `buttontext` | `#ffffff` | **白** |

**按名义配对全部可读**：`windowtext`/`window`、`text`/`base`、
`buttontext`/`button` 都达标——这就是前两版检查后「无异常」的原因。

但它是坏的，只是坏在别处：`buttontext` 是纯白，而 `window` 与 `base` 都是浅色。
**任何在 window/base 上绘制 `ButtonText` 的控件，都是白字白底。**

更关键的是：**只要 `button` 还是黑的，就不存在任何一种文字色能同时在白底和黑底上
可读**。所以只改文字色解决不了——第一版尝试就证明了这点，它把已修好的 `WindowText`
又改回近白色。

**修复**：先把背景对齐到同一亮度侧，再选文字色。

- 以 `Window` 为基准（窗口面积主体，且三个背景里两个已经是亮的）；
- 落在错误一侧的背景重新着色并打警告；
- 之后再用对齐后的背景复核文字角色。

样式本来选对的背景不动。

新增 `deviceOhosPaletteIsRepaired`，用设备调色板原文验证：先断言名义配对**确实可读**

在读取前已析构，所有颜色打印成 `#`。改为 `QByteArray` 局部变量。

### 本轮产出：控件级诊断

既然应用级数值正常而控件仍不可见，诊断下沉到控件。`UpdateStyle()` 切换后对
主菜单栏与颜色名按钮各输出一行：

```
LEOCAD_THEME_WIDGET {"widget":"menubar","enabled":true,"has_own_palette":false,
  "own_style":false,"style_class":"...","app_style":"...",
  "windowtext":"...","buttontext":"...","text":"...",
  "window":"...","button":"...","base":"...","has_stylesheet":false}
```

字段的用途：

| 字段 | 为什么重要 |
|---|---|
| `has_own_palette` | `WA_SetPalette` 为真时控件**不再跟随应用调色板**，而清除应用样式表也不会重置它——宿主实测：显式设置后应用调色板变更对它无效，清空后才重新继承 |
| `own_style` / `style_class` | 控件可能被与应用不同的样式绘制 |
| `has_stylesheet` | 控件自身样式表会覆盖调色板 |
| `enabled` | 取的是 Active 还是 Disabled 颜色组 |
| 六个颜色 | 控件**实际解析**到的值，与上一条应用级日志对照即可定位断点 |

宿主输出正常（`has_own_palette:false`、`style_class` 与应用一致、六个颜色可读），
因此设备上的差异才是要看的。

### 为什么桌面测试抓不到

桌面 `style()->objectName()` 是 `"fusion"`，还原路径总成功。而且即使注入空名，
桌面 `standardPalette()` 取自当前仍生效的 Fusion，配色仍是浅色、对比度正常。
**所以只断言「对比度够」在原理上抓不到这个缺陷**——我第一版就是这样，把修复撤掉
测试照样全绿。

真机的差别在鸿蒙样式本身的 `standardPalette`。断言必须落在**「还原是否真的发生」**
上，而不是它的下游效果。

### 修复

两层，都在 `common/lc_application.cpp`：

1. **构造时兜底**：`objectName()` 为空则取 `metaObject()->className()`，并去掉
   `Style` 后缀与前导 `Q`，得到 `QStyleFactory::keys()` 认得的键（`QFusionStyle`
   → `Fusion`）。已实测该转换能通过 `setStyle()` 解析。
2. **还原失败时兜底**：`setStyle()` 返回 null 就显式记录警告，回落到 `Fusion`
   （键表里没有则取第一个可用样式），并**把回落值写回 `mDefaultStyle`**，下次切换
   不必再猜。

第 2 层同时让「还原失败」这件事不再静默：原来的代码完全忽略返回值。

### 本轮撤掉的两处无法验证的改动

| 曾加入 | 为何撤掉 |
|---|---|
| 切换后对全部控件 `unpolish()/polish()/update()` | 撤掉后用例仍全绿——桌面上 Qt 自动传播调色板。无法在本机证明必要，就不能算修复的一部分 |
| 「先 setPalette 后清样式表」的顺序缺陷断言 | 桌面两种顺序结果相同，用例抓不到差异 |

顺序本身仍改为「先清样式表、后设调色板」：清空样式表会移除 `QStyleSheetStyle`
这一层，调色板必须设在其后的样式上。**这是语义推理，不是本机可证的结论**，
代码与用例注释均已如此标注。

`appliedPaletteSurvivesTheStylesheetTeardown` 因此限定为「修复后的角色确实到达会绘制的
控件」，不声称证明了顺序。
| `readablePaletteIsLeftAlone` | 健康调色板原样返回 |

用 WCAG 2.1 相对亮度算对比度；健康配色在 11–21 之间，阈值取 4.5（AA 正文级）。
`UpdateStyle()` 由 protected 改为 public，并加 `GetDefaultStyleName()` /
`SetDefaultStyleName()`，因为要复现设备状态就必须能把名字置空。

**回归验证**：

| 改坏的行为 | 结果 |
|---|---|
| 把 `setStyle(Fallback)` 换成「只回填名字、不应用样式」 | **失败**：`the window colour is still #d4d0c8 ... the fallback was recorded but not applied` |
| 去掉 `UpdateStyle()` 内的回填 | 失败：`the default style name is empty` |
| 去掉构造时兜底 | 通过——第 2 层已覆盖，属双保险而非假通过 |

第一条是本轮评审发现的关键缺口。**第一版测试抓不到它**，两次尝试都失败：

1. 只断言对比度——桌面上 `standardPalette()` 取自仍生效的 Fusion，配色本就是浅色；
2. 只断言 `mDefaultStyle` 非空 + 样式非空——注入空名后回填即满足，与是否真的换了
   样式无关。

最终做法：先注入 **Windows** 样式（其 `standardPalette().Window` 是 `#d4d0c8`，
与 Fusion 的 `#efefef` 不同），再构造空默认名，断言切换后 `Window` 颜色**不再是**
注入样式的值。评审用 `style()!=nullptr` 替换 `setStyle(Fallback)` 的 mutation 下，
该断言立即失败。

**为什么不用样式类名比较**：装了样式表后 `QApplication::style()` 是
`QStyleSheetStyle` 包装，类名与底层样式无关，比较恒等——我试过，测试因此假通过。

### 8.1 给 A 的 D4-01 线索

代码路径：

```cpp
// common/lc_view.cpp:800
mRenderImage = QImage(Width, Height, QImage::Format_ARGB32);

// common/lc_view.cpp:833
QImage lcView::GetRenderFramebufferImage() const { return mRenderFramebuffer->toImage(); }

// common/lc_view.cpp:962 —— 裸 memcpy，按 4 字节/像素假设通道顺序
memcpy(dst, src, CurrentTileWidth * 4);
```

`QOpenGLFramebufferObject::toImage()` **不保证**返回 `Format_ARGB32`，格式随平台。
设备日志确认是真 GLES（`is_gles: true`、`OpenGL ES 3.2`），GLES 上通常是
`Format_RGBA8888`，相对 ARGB32 红蓝互换——这与「Red 显示成 Blue」吻合。

但**没有证明**：LightBlue 显示偏黄不是单纯红蓝互换，可能是另一条路径（缩略图管理器
的 `convertToFormat`，或颜色值本身）。建议 A 在真机打印 `toImage()` 的实际
`format()`，再决定修哪里，而不是按线索直接交换通道。

我试过一版修复（在 memcpy 前判断格式并 `convertToFormat(Format_ARGB32)`），
代码已撤回，未提交。
