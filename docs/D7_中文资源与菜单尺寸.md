## 1. 三条反馈的根因

| 反馈 | 根因 | 性质 |
|---|---|---|
| `Filter Parts`、`Parts` 计数、空态仍为英文 | 新串从未进入 `.ts`；计数串当年刻意避开 `%n part(s)` 但没补翻译 | 缺翻译 |
| 分类、颜色名称未统一中文 | 这两类**是数据不是文案**，不能原地翻译（见 §2） | 需要在显示层做 |
| 筛选子菜单 `Regular...ression`、`显示...零件` 被省略 | 菜单在 `aboutToShow` 里清空重建，而 Qt 在那之前已算好宽度 | 尺寸顺序 bug |

第三条最容易被误判成「翻译没做」或「屏幕太窄」。它不是：同一菜单里比 `Regular
Expression` 更长的 `Part Description` 显示完整，只有它被截断——宽度是按上一次内容算的。

## 2. 为什么分类名和颜色名不能原地翻译

两条硬约束：

- `lcLibraryCategory::Name` 是 profile 往返用的键（`lcSaveCategories()` 写、`lcLoadCategories()` 读），也是用户自定义分类文件匹配的依据。翻译它，等于让一种语言下保存的配置在另一种语言下失效。
- `lcColor::Name` 是 `char[64]`（`LC_MAX_COLOR_NAME`），会写进模型文件、导出文件和颜色配置。翻译它既改变保存值，又会在译文超过 64 字节时截断。

所以把翻译放在**显示点**：新增 `lcGetCategoryDisplayName()` 和 `lcGetColorDisplayName()`，
存储值一个字节不动。测试同时盯两头——存储值仍是英文，显示值是中文，任何一边退化都会失败。
`lcGetColorToolTip()` 也改走同一函数，避免 tooltip 和颜色按钮措辞漂移。

翻译按 context 分开：分类名进 `Categories`，颜色名进 `Colors`。否则 300 多个颜色名会淹没
通用 context，后面的人很难维护。

## 3. 菜单省略的修法

在 `lcPartSelectionWidget::SetMenuWidthToContents()` 里按实测文本设最小宽度，并递归到子菜单。

试过但**无效**的方案，记录在此以免重复：

| 方案 | 结果 |
|---|---|
| `adjustSize()` | 无效，宽度不变 |
| 构造时预填充、`aboutToShow` 只改勾选态 | 无效，仍是旧宽度 |
| 用 `sizeFromContents()` 推导所需宽度 | 在 offscreen/wayland 下低报，不可靠 |
| `setMinimumWidth(实测文本宽 + 样式开销)` | **有效**，子菜单需各自调用 |

本机对照数据（`QT_QPA_PLATFORM=offscreen`，同一次构建）：

```
修复前: 主菜单宽=221(需259)  Filter子菜单宽=100(需205)
修复后: 主菜单宽=259(需259)  Filter子菜单宽=205(需205)
```

真机上两种窗口尺寸的选项菜单都是 204×136，与窗口宽度无关——这正是修复的要害：
菜单宽度不该由屏幕或上一次内容决定。

## 5.1 字体：D7 要求里的另一半

「中文资源、字体和常用提示」里的**字体**一项，缺陷表此前没有任何记录，本轮补上。

翻译正确但字体缺字形时，屏幕上是空白或方框，看起来和「没翻译」一模一样。所以这一项必须单独测，
不能靠「字串已经在 .ts 里」推断。

`chineseGlyphsAreAvailableToTheUiFont()` 初版从 `.ts` 取出实际显示的全部中文，逐字问
`QFontMetrics::inFont()`。**它在 Windows CI 上失败、在 Linux 上通过**——不是 Windows 缺字体，
是 `inFont()` 的语义随引擎不同：Linux 的 fontconfig 把回退并进字体本身（所以逐字都答「有」），
Windows 的 DirectWrite 只答「这个 family 自己有没有」（Segoe UI 对所有中文答「没有」，尽管绘制时
逐串回退到微软雅黑照样画得出）。一个跨主机断言测的其实是宿主字体栈，不是产品。

改成只断言**所有引擎都给得出**的东西：`.ts` 可读且四个 context 都有译文、行高 > 0、以及
`horizontalAdvance("测试")` > `horizontalAdvance("ab")`——真画不出中文的环境，这个测量会塌成 0。
逐字字形覆盖归给 `tools/d7/tst_d7_fonts.cpp` 探针：**在真机上跑**，那里的字体集才是发布对象。

**同一个测试在 Windows 上第二次红**，这次是 `Metrics.ascent() > 0 && Metrics.descent() > 0`：
DirectWrite 对回退到的微软雅黑报告**排版语义**（`sTypoDescender = 0`，字形实际下沉由
`descender` 负值另记，只为凑 `tmAscent+tmDescent+tmLineGap = tmHeight`），fontconfig 报告
**上下文语义**（descent 是字形真正占的下半格，>0）。两边都“对”——它们回答的不是同一个问题。
当时留下的 `height >= ascent + descent` 在 Windows 通过，靠的正是这个恒等式的构造，不是引擎
承诺；两次连续的红绿翻转说明，**只该断言语义无歧义的量**，而 `a+d<=h` 依赖半值的语义解释，
于是也移除了，连同注释一起留下这条规则。CJK 测量宽度大于拉丁是跨引擎有定义的命题：全角字 ≈
1em，无论排版还是上下文语义都大于拉丁平均半宽。

**负向验证（修正版）**：把 `.ts` 从仓库移走，测试准确报出
`no Chinese translations were read from the .ts`；恢复后通过。

`chineseTextIsNotWiderThanTheSpaceItsEnglishPredecessorHad()` 检查中文译名不比它替换掉的英文宽
（这条两边都成立：CJK 全角单字 ≈ 1em，同义中文串字数少一半以上，对具体字体不敏感）。
菜单宽度按最长项算，只断言「现在放得下」的话，翻译变长时宽度跟着变、测试仍绿，掩盖了要看的事。

**负向验证**：初版曾往「筛选零件」注入 U+12000 楔形文字（无任何 CJK 字体收录），测试准确报出
缺失字符；恢复后通过。（更早的弯路：用「不存在的字体族」伪造缺字无效——Qt 按字符回退照样画出，
这在 Linux 侧是 true，也正是 Windows 侧 false 的另一面。这个弯路说明**负向验证本身可能无效**，
注入的破坏必须打在断言真正依赖的机制上。）

宿主实测（`tools/d7/tst_d7_fonts.cpp`，见 §5.3）：28 个字体族里 17 个提供简体中文，
全部采样中文 `missing=0`，`筛选零件 = 48 px` 对比 `Filter Parts = 63 px`，中文更窄。

## 5.1b Windows CI 的一个连带发现：九个套件的日志一直是空的

排查这次 Windows 失败时发现，`Run-D3Tests.ps1` 用 PowerShell 的 `*>` 把测试二进制输出重定向到
`test-results.txt`——**在 runner 上落盘的一直是 0 字节**（同仓库 `Build-MemberB.ps1` 用 QtTest 自带
的 `-o file,txt` 就正常）。套件判定靠「退出码非 0 或日志里有 `FAIL!`」：空日志里永远没有 `FAIL!`，
于是 Windows 上 9 个套件过去只由退出码把关，**日志层面长期失明**，#41 与本次所有「绿」都没有一条
PASS 行作证据。

已改为与 `Build-MemberB.ps1` 相同的 `-o` 方式，并把退出码和字节数打回 console（崩溃在首次 flush
之前时，退出码是唯一信号，至少要可见）。

**教训**：重定向对原生进程「看起来成功」不等于拿到输出；采集机制要用被测程序自己的落盘选项，
并且失败时能区分「没跑」与「跑了但看不到」。空的成功日志比缺失的日志更危险。

## 5.2 常用提示：文件打不开时的对话框

「常用提示」挑的是打开/保存失败时会弹出的 `QMessageBox` 正文，共 17 条，本轮全部翻译。这些是
用户在正常操作中就会撞见的（打开一个坏文件、另存为不支持的格式），英文提示等于一个全英文对话框。

`commonFileErrorMessagesAreTranslated()` 逐条断言已翻译，并单独检查格式串没有丢掉 `%1`/`%2`——
丢占位符会让用户直接看到 `%1`，和漏翻是两种不同的错。

**没有翻译的**：命令行 `--help` 的 51 条参数说明。鸿蒙首发版没有命令行入口，这些串到不了用户面前；
翻了只会给日后跟进增加负担。若后续要做桌面端中文，需要单独立项。

## 7. 边界与未完成项

**这批截图不是真机截图。** 是 x86_64 宿主上 WSLg Wayland + `QWidget::grab()` 生成的。真机
（HAD-W32 / API23 / Qt6.12 / ARM64）复验仍由组长按计划执行。**本次不宣称已通过真机验收。**

**3D 视口在截图里是空白的。** `QWidget::grab()` 取的是 widget backing store，`QOpenGLWidget`
画在自己的 FBO 里，不属于它。GL 本身正常（`framebuffer_status: 36053` = `GL_FRAMEBUFFER_COMPLETE`，
`passed: true`）。D7 没有动 3D 视图，但这批图不能当作渲染正常的证据。同样的原因，
`narrow-1280x800-window.png` 不是字节可复现的（缩略图异步渲染），已在 `tools/d7/README.md` 记明。

**三类问题不随本次修复关闭：**

- D4-01 缩略图颜色（[#27](https://github.com/xiaotaop/leocad-harmony/issues/27)，A 主责 / C 配合）。这是渲染通道问题，用翻译修复去替代它是不可接受的。
- 偏好设置剩余裁剪（[#14](https://github.com/xiaotaop/leocad-harmony/issues/14)）。
- 系统文件选择闭环（#15）。

**还有 75 条英文串没有翻译。** 以 `origin/main` 为基线（当时 97 条）本轮修好 22 条，剩余 75 条，
没有新增缺口。分两类：

- **51 条命令行串。** `--help` 的参数说明，以及只有命令行路径会打印的 `StdOut`/`StdErr` 消息
  （`Saved '%1'.`、`The file '%1' is not readable.` 等）。鸿蒙首发版没有命令行入口，这些串到不了
  用户面前，翻了只是给日后跟进增加负担。
- **24 条专业参数。** 相机与灯光的属性字段（`Camera name`、`Camera projection`、`Cone Angle`、
  `Penumbra Angle`、`Power of the light in Watts` 等）。这些需要先定术语表才能翻，逐词直译会
  得到半通不通的中文，比英文更难懂。其中 `POV-Ray Export` / `Blender Settings` 属于 #14 的
  裁剪范围，翻译等于给即将移除的控件做中文。

两类都不在 F-02（组长报告的是零件面板）范围内，未在本轮一并处理；若要纳入首发中文范围，需要
单独立项，且需要先定专业术语表。

**应用材料与隐私说明**（D7 四项里的最后一项）：`docs/release/` 六份文档已有初稿。本轮做了三件
超出「写文档」的事，因为写的过程中发现文档本身有问题：

1. **六份文档此前从未进入版本控制。** `.gitignore` 第 33 行的 `release` 是裸模式，本意是忽略根目录
   的 qmake 影子构建输出，连 `docs/release/` 一起吞掉了。源码获取说明和第三方组件清单是 GPL-2.0
   的分发义务，丢文件是授权问题。已改为 `/release`（第 61 行本来就有锚定规则），六份文档入库。

2. **改掉了三处已经过时的说法。** `已知问题.md` 原写「颜色名仅覆盖 52 个常用色」并指向
   `resources/color_names_zh.tsv`——该文件不存在，`Colors` 实际有 337 条译文覆盖 `ldconfig.ldr`
   全部 322 色；I-01/I-04 的「约 70 条 / 7 条」实测是 51 条且互相包含；F-02 仍以未修口吻描述。
   发布评审读的是这份文档，数字必须能从构建里复核出来。

3. **核查隐私声明时发现一个 P0，见 `docs/release/已知问题.md` §5.1。** 「不申请网络权限」的依据是
   功能裁剪（`ApplyFirstReleaseScope()` 移除了 Blender 和 BrickLink 库存下载入口），不是代码里

   访问 `leocad.org/updates.txt`**。这一条交给了 `scripts/library/test_network_scope.py` 静态锁定
   （已接入 CI 的 port-policy 作业，之前没有任何 CI 步骤跑 Python 测试）。

**仍未解决的 7 处 `[待补]`**（开发者信息、商店类目、公开仓库 URL、发布标签名、签名包对应提交）
