# 源码获取说明（GPLv2 合规）

> 负责人：成员 C　性质：GPL-2.0 分发义务的落实说明
> 状态：**初稿**。仓库侧证据基本齐备，**包内呈现尚未实现**（§3），
> 两个由组长掌管的标识仍未提供（§4），Qt 兼容性裁定未闭环（§8 自检表、§9 待办）。

## 1. 法律依据

本应用包含 LeoCAD 的修改版本，以 GNU General Public License version 2 发布。
GPLv2 要求任何分发二进制的一方同时提供：

1. 许可证全文（GPLv2 正文）；
2. 版权声明；
3. **对应的完整源码**，或有效的书面获取方式（GPLv2 §3）。

本项目同时包含 LDraw 零件库子集（CC BY 4.0），该部分只需署名，不要求提供源码；
其署名义务的落实状态见 `docs/release/第三方组件清单.md` §4.1 与 §5.5（**亦为阻断项**）。

### 1.1 版本形态：GPLv2-only 的处置

LeoCAD 上游声明为 "GNU General Public License version 2"（`README.md:91`），
**没有 "or later" 字样**。按 `docs/ui/D1_界面清点与首发范围原则.md` §5.3 的治理原则，
一律按 **GPLv2-only** 处理，不把 "version 2" 解释为 "version 2 or later"。

- `COPYING:242-248`（"If the Program specifies a version number … and 'any later version'"）
  是版本选择条款本身；本项目未作 or-later 声明，该条不适用。
- `COPYING:282-299` 是 GPL 附录给新程序的**样板通知示例**，不是本项目的授权声明。

因此本文件所有义务都按 GPLv2-only 的最严口径列写；兼容性裁定见 §8。

## 2. GPLv2 §3 的硬性要求（逐条对齐 `COPYING:134-170`）

分发二进制时，必须做到下列三者**之一**（`COPYING:136`）：

| 选项 | 原文位置 | 要求 |
|---|---|---|
| (a) 随附源码 | `COPYING:138-140` | 直接用惯用介质附带**完整对应源码**，并按 §1、§2 授权 |
| (b) 书面要约 | `COPYING:142-147` | 附一份**书面要约**，见下方硬性条件 |
| (c) 随附他人要约 | `COPYING:149-153` | **仅限非商业分发**，且须是收到程序时已附带的要约——本应用经应用市场分发，**该选项不适用** |

若采用 (b) 书面要约，硬性条件如下（**缺一不可**）：

1. **有效期至少三年**（`COPYING:142`，"valid for at least three years"）；
2. **对任何第三方有效**（"to give any third party"）——不能只对购买者、只对国内用户、
   或要求先注册；
3. **收费不得超过实际执行源码分发的成本**（`COPYING:143-144`，
   "no more than your cost of physically performing source distribution"）；
4. 提供的是**完整的机器可读源码副本**，并按 §1、§2 授权；
5. 载体须是**惯用于软件交换的介质**（"on a medium customarily used for software interchange"）。

"完整源码"的口径（`COPYING:155-164`）同样有硬要求：

6. 必须是**修改它所需要的首选形式**（preferred form for making modifications）；
7. 对可执行作品，**包含其中所有模块的全部源码**，加**接口定义文件**；
8. **包含用于控制编译与安装的脚本**（"the scripts used to control compilation and
   installation of the executable"）。

第 8 条是本文件 §5.2、§5.3 的直接依据：构建脚本属于"完整源码"的一部分，
不能只给 `common/`、`qt/` 目录，也不能留下一段无法复现的重建流程。

GPLv2 §3 末段（`COPYING:166-170`）另有一条常用途径：若分发方式本身是提供**指定位置**
的复制访问，那么在同一位置提供源码的等效访问即视为分发源码。**公开仓库地址即按此条成立**，
前提是地址长期有效且与所分发二进制对应（见 §4）。GPLv2 §3 末段原文：
"If distribution of executable or object code is made by offering access to copy from a
designated place, then offering equivalent access to copy the source code from the same place
counts as distribution of the source code"。

### 5.2 零件库：分发现成档案，按清单哈希校验

零件库**不从官方库现场重建**。发布包内的 `assets/ldraw-lite/library-lite.zip`

| 字段 | 值 | 实测 |
|---|---|---|

| `archive.sha256` | `09922e82d157dd1e3906661db44384bf212b9e065bb0205f8fd1702e4268c0f3` | `sha256sum` 一致 |
| `archive.bytes` | `3833541` | `stat` 一致 |
| `counts.total_files` | `2741` | `zipfile` 实测 2741 条目 |

外部第三方核验方式：

```bash
sha256sum assets/ldraw-lite/library-lite.zip
# 期望：09922e82d157dd1e3906661db44384bf212b9e065bb0205f8fd1702e4268c0f3
python3 scripts/library/test_packaged_resources.py   # 校验 qrc 引用与档案摘要
```

**已知缺口（必须写明）**：`manifest.json` 的 `generator.script` 指向
`scripts/library/build_library.py`，但该脚本以及 `generate_selection.py`、
`verify_library.py` **在仓库中均不存在**（全仓 glob 核实）。因此：

- "从官方库重建同一档案"的能力**目前不具备**，任何材料都不得这样承诺；
- 现阶段可复现的只是"档案内容与清单声明一致"，不是"档案可由脚本重新生成"；
- 补齐这三个脚本是后续工作项，责任人待指派；补齐前，上游库若有更新，只能人工重做并重签清单。

### 5.3 构建步骤（现状）

1. 按 `toolchain.lock` 安装指定的 DevEco 命令行工具、HarmonyOS SDK/NDK、

2. 使用根 `CMakeLists.txt` 构建 HAP/APP（`OHOS` 目标）；
3. 零件库直接使用已提交的 `library-lite.zip`，不做重建（§5.2）。
