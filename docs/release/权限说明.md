## 2. 逐项说明

判断"要不要"时请注意两条边界：**请求权限 ≠ 使用权限**（链接了 Qt 模块不等于调用了系统能力），
**这条能力在首发版不可达 ≠ 这一行可以立刻删**（删行要重打包、要过 RC0 验证）。

### 2.1 `STORE_PERSISTENT_DATA`（应用自有的持久化存储）

- **产物声明**：是，无 reason / usedScene。
- **关联功能**：偏好设置与"最近文件"列表的本地持久化。依据：`common/lc_profile.cpp:181-258`
  （`QSettings` 读写）、`common/lc_mainwindow.cpp:49-71`（`lcGetProfileString` /
  `lcSetProfileString` 加载与保存最近文件）。
- **项目是否声明**：否，本仓库无声明点（见 §0）。
- **拒绝 / 删除后的降级**：应用应仍能启动，设置在本次会话内有效、退出后丢失。
  **这是推断，未在真机验证**——设置目录本身在沙箱内，是否需要该权限属系统侧行为。
- **建议**：保留（暂定）。只有组长在 RC0 上验证"删掉后偏好仍持久化"才可移除。

### 2.2 `FILE_ACCESS_PERSIST`（文件选择结果的可持久访问）

- **产物声明**：是，无 reason / usedScene。
- **关联功能**：打开 / 保存用户主动选择的模型文件。依据：`common/lc_mainwindow.cpp:2803`
  （`QFileDialog::getOpenFileName`）、`:2938`（`QFileDialog::getSaveFileName`）。
- **边界**：应用**不**遍历目录、不扫描存储。`getOpenFileNames` 唯一调用点 `:2849` 属
  "合并模型"，该命令已在首发版移除（`common/lc_mainwindow.cpp:667` `LC_FILE_MERGE`）。
- **拒绝 / 删除后的降级**：每次打开/保存都要重新经系统选择器；"最近文件"可能无法直接重开。
  **未在真机验证**。
- **建议**：保留。

### 2.3 `PREPARE_APP_TERMINATE`（终止前准备）

- **产物声明**：是，无 reason / usedScene。
- **项目是否声明**：否。**本仓库也没有任何调用点**：`grep -rn 'PREPARE_APP_TERMINATE' common/ qt/`
  无命中；应用自身只在 `common/lc_mainwindow.cpp:1316`（`closeEvent`）处理关闭。
- **推断**：带 `qt_` 前缀的同类项（见 §3）与 Qt 运行时行为一致，倾向于是 Qt 模板为
  "优雅退出/保存状态"预留的权限，**但没有证据**。
- **拒绝 / 删除后的降级**：未知。若 Qt 运行时依赖它，删除可能导致退出时来不及保存状态。
- **建议**：保留（暂定）。删除前必须由组长确认 Qt HarmonyOS 运行时是否使用该能力。

### 2.4 `READ_PASTEBOARD`（读取剪贴板）— 必须保留

- **产物声明**：是，**且是 6 项里唯一带 `reason` 与 `usedScene` 的**：
  `"reason": "$string:qt_permission_reason_read_pasteboard"`，`usedScene` 为
  `QAbility` / `when: always`。`reason` 串带 `qt_` 前缀，且本仓库无该字符串资源（grep 无命中），
  说明它同样来自 Qt 模板 —— **用户看到的用途文案不由我们撰写**（见 §5 待确认项）。
- **复制链路（写）**：`common/lc_model.cpp:1180-1188`（`lcModel::Copy()`）→
  `common/lc_application.cpp:772-780`（`ExportClipboard`，`:777` `setMimeData`）。
- **读取链路（监听）**：`common/lc_mainwindow.cpp:132-133` 连接 `QClipboard::dataChanged`
  并在构造时先调用一次 → `:1452-1462` `ClipboardChanged()`。
- **粘贴链路**：`common/lc_mainwindow.cpp:3168-3171`（`LC_EDIT_PASTE`）→
  `common/lc_model.cpp:1190-1193`。
- **菜单**：剪切/复制/粘贴在 Edit 菜单保留（`common/lc_mainwindow.cpp:532-535`）；
  `LC_EDIT_PASTE_STEPS` 被移除（`:685`），不影响单步粘贴。
- **拒绝授权后的降级行为（静态核对结论——不崩溃，功能降级）**：
  1. `ClipboardChanged()` 对返回值判空后才取数据（`common/lc_mainwindow.cpp:1458`
     `if (MimeData && MimeData->hasFormat(MimeType))`），读不到剪贴板不会解引用空指针；
  2. 读到空内容时 `SetClipboard` 传入空 `QByteArray`（`common/lc_application.cpp:766-770`），
     随即 `UpdatePaste(false)` 把"粘贴"置灰（`common/lc_mainwindow.cpp:2510-2517`）；
  3. 粘贴入口另有空内容短路：`common/lc_model.cpp:1192-1193` 直接 `return`；
  4. 复制（写剪贴板）走 `setMimeData`，不读系统剪贴板，因此**不依赖**该项授权即可完成写入。
- **设备侧佐证**：2026-10-29 至 11-02 的多份 hilog 均出现
  `ohos.permission.READ_PASTEBOARD hasn't been granted by user. Cannot read pasteboard data.`
  （例如 `docs/evidence/leader/2026-11-02/d7-device/final-first-session.hilog.txt:47`），
  而同一次会话的应用启动、文件读写、渲染验收均通过 —— **未授权时应用可正常启动、核心闭环不受阻**。
  这条现象与 issue #16 记录的"设备日志存在 READ_PASTEBOARD 未获用户授权"一致。
  注意：日志只证明"启动不受阻"，**没有**证明"点击粘贴后的用户可见行为"，那需要真机复测（§5）。
- **建议**：**必须保留**。这是唯一一项有明确代码证据支持其必要性的"运行时可能被拒"权限。
  按 issue #16 的要求，应用**不得**用自动授予权限的方式绕过用户决定；当前代码也没有这样做。

### 2.5 `GET_FILE_ICON`（获取文件图标）— 建议移除

- **产物声明**：是，无 reason / usedScene。
- **项目是否使用**：**没有任何使用点**。`grep -rn 'QFileIconProvider|QIconProvider|fileIcon|FileIcon'`
  在 `common/`、`qt/` 下 **0 命中**；进一步核对文件浏览类控件
  `grep -rn 'QFileSystemModel|QDirModel|QTreeView'` 同样 **0 命中**——首发版没有任何展示文件
  图标的 UI，因此"获取文件图标"这项能力在界面上无处可去。
- **拒绝 / 删除后的降级**：无（没有调用点）。
- **建议**：**建议移除**。风险低，但"删除后包能否构建/启动"必须由组长在 RC0 验证（§5）。

### 2.6 `PRINT`（打印）— 建议移除，但结论要谨慎

- **产物声明**：是，无 reason / usedScene。
- **打印画面在首发版不可达**（静态核对）：
  1. 命令已从菜单移除：`common/lc_mainwindow.cpp:658-659`（`ApplyFirstReleaseScope()` 的
     `RemovedCommands[]` 含 `LC_FILE_PRINT`、`LC_FILE_PRINT_PREVIEW`）；
  2. 移除后动作被显式禁用：`common/lc_mainwindow.cpp:781-782`
     （`Action->setVisible(false); Action->setEnabled(false);`）——被禁用的 `QAction`
     不会响应快捷键；
  3. 两个命令的默认快捷键为空串：`common/lc_commands.cpp:140-153`（第 145、152 行 `""`）；
  4. 处理函数 `common/lc_mainwindow.cpp:1716`（`ShowPrintDialog`）只在
     `:3133-3134`（`case LC_FILE_PRINT`）被调用，而进入 `HandleCommand` 的唯一入口
     `:1472` 由 `ActionTriggered` 的 `sender()` 驱动；
  5. 说明文档对话框 `ShowInstructionsDialog()`（`:1708`）只被 `:3125-3126` 的
     `LC_FILE_INSTRUCTIONS` 调用，该命令同属移除列表（`:660`），因此
     `lcInstructionsDialog` 里的打印按钮（`common/lc_instructionsdialog.cpp:576-591`）也不可达。
- **但**：
  - Qt PrintSupport 仍被链接（`CMakeLists.txt:90`、`leocad.pro:2`），`QPrinter`/`QPrintDialog`
    仍在编译产物里（`common/lc_mainwindow.cpp:3,1721-1724`、`common/lc_global.h:14-15`）；
  - **请求权限 ≠ 使用权限**：Qt 模板可能为 PrintSupport 的默认行为申请该项，即便我们从不打开打印对话框；
  - 因此结论不是"必须删"，而是"**本项目用不到它，建议移除，并由组长确认 Qt 模板不再需要**"。
- **建议**：**建议移除**。风险低（打印本就不在首发范围），但依赖 RC0 重打包验证。

## 3. Qt 注入 vs 本项目声明

| 观察 | 推断 | 依据强度 |
|---|---|---|
| 6 项全部出现在 Qt 模板产出的清单里，本项目无任何 `requestPermissions` 写入点 | 6 项均为 **Qt 模板默认注入** | **强**：`CMakeLists.txt:111-119` 复制模板；全仓库 grep 无声明点 |
| 只有 `READ_PASTEBOARD` 带 `reason`/`usedScene`，其字符串键以 `qt_` 开头 | 该项是模板为剪贴板准备的"标准样例" | **强**：产物原文 + 仓库内无该字符串资源 |
| 其余 5 项无 `reason`/`usedScene` | 可能属系统级授权（无需用户确认，故不需要 reason） | **弱（推断，未查证）**：无法访问华为权限分级文档，本机也无 HarmonyOS 文档，**不能**当结论用 |

**由此得出的一条工作纪律**：本项目要"减少权限"，改的是**模板副本/DevEco 工程**，
不是本仓库的代码；而且 `CMakeLists.txt:116-117` 每次构建都会从 Qt 安装目录重新 `file(COPY)`，
**在 build 目录里手改 `module.json5` 会在下一次 clean build 时被覆盖**。

### 4.1 reason 字段与实际展示内容核对

## 6. 网络：明确不申请（结论不变，并已由产物证实）

首发版无联网功能，因此**不在 `module.json5` 中声明 INTERNET 权限**。这一点在
2026-11-02 的 D7 产物中已直接核对（`grep -c ohos.permission.INTERNET` = 0），
不再是"待确认"项。

构建层依据（此前写"需组长确认"，核查实际 CMake 配置后更正）：鸿蒙构建走根
`CMakeLists.txt`，第 75–82 行对 `leocad` 目标**无条件**定义 `LC_DISABLE_UPDATE_CHECK=1`，
`if(OHOS)` 内另加 `LC_DISABLE_NETWORK=1`。`scripts/build-harmony-app.ps1` 配置的正是这套
CMake 工程，`qtmain.cpp` 的启动更新检查分支因此不参与编译。OHOS 目标也不链接
`Qt6::Network`（`CMakeLists.txt:93-95` 的 `if(NOT OHOS)` 才链接）。

**`LC_DISABLE_NETWORK` 覆盖不到的一类：外部网址。** 该宏只把 `lc_http` 换成空实现，不拦截
`QDesktopServices::openUrl`。帮助菜单的「主页」「报告问题」正是这样打开 `https://www.leocad.org/`
与 GitHub issues 的——应用自身不发请求，但会拉起浏览器联网，与本文档和隐私政策的离线承诺冲突。
D8 界面冻结时发现这两项此前无任何拦截，现已从菜单移除（列入 `ApplyFirstReleaseScope()`），
并由静态检查与窗口级菜单测试锁定。**没有网络权限不等于没有任何联网动作**，这两层要分别核对。

## 7. 应用沙箱目录（不需要额外权限）

| 目录 | 内容 | 清理方式 |
|---|---|---|
| 应用数据目录 | 偏好设置、零件库副本 | 清除应用数据 |
| 应用缓存目录 | 零件索引缓存 | 系统可回收，应用可重建 |
| 临时目录 | 保存时的临时文件 | 保存成功后替换，失败则清理 |

`lcPiecesLibrary::FindBundledLibraryArchive()`（`common/lc_library.cpp:285`）优先使用应用数据
目录中的 `ldraw-lite/library-lite.zip`；该副本由平台层在首次运行时展开。**这部分按当前设计
不需要沙箱外权限**——但若 RC0 发现首次展开失败，需回到这里复核（§5 未覆盖的潜在项）。

## 10. 时效性

本文档的权限结论**绑定在 2026-11-02 的那一次 D7 构建上**（`module.json5` 与 HAP SHA-256 见 §0）。

以下任一情况发生，必须重新核对并更新本文档，不能沿用：

1. 更换 Qt HarmonyOS 版本（模板可能增减默认权限）；
2. 重新打包 / 重新签名（清单可能被 DevEco 工程覆盖）；
3. 恢复任何联网入口（Blender 附加组件、BrickLink 库存、更新检查、外部网址）——那不是"加不加
   INTERNET 权限"的问题，隐私政策第 1 节要同时复审；
4. 恢复打印 / 说明文档功能（`PRINT` 就不再是"建议移除"）；
5. 恢复基于文件的 UI（`GET_FILE_ICON` 的理由要重新评估）。

### 自动化覆盖到什么程度

D10 之前本仓库**没有任何自动化检查**涉及权限清单：`scripts/library/test_network_scope.py`
只守住"构建宏 + 菜单裁剪"，其文件头（`:24-27`）自己就写明"打包清单是不是申请了 INTERNET
是另一个问题，由发布文档核对，不由本文件检查"。

D10 新增 `scripts/library/test_permission_scope.py`（5 项，已接入 `continuous.yml` 的
port-policy job），守住的是**文档与记录产物之间的一致性**：

- 记录产物里出现的每一项权限，必须在本文件里出现（清单增加而文档不写 → 失败）；
- 记录产物里不得出现 `ohos.permission.INTERNET`（离线承诺的清单侧）；
- 标为"建议移除"的行必须带上理由，不能是一行光秃秃的建议。

它**不能**替代 RC0 的人工核对：仓库里没有构建、Qt 模板也没 vendor 进来，脚本读的是
`docs/evidence/leader/2026-11-02/d7-device/packaged-module.json5` 这份**留档副本**，
不是当晚打出来的包。所以下面这条仍然是人工项：

> **RC0 必须解包新 HAP、核对 `module.json5` 的 `requestPermissions`，与本文件逐项对照，
> 并把权限差异与包 SHA-256 留证。**（issue #16 的验收要求）
