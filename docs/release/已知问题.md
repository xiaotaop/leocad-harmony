> 负责人：成员 C　状态：持续更新，RC2 前定稿

D10 的鸿蒙中型模型验收目标是 2,000 个零件实例，样例包含 16 种网格和 4 个子模型。设备验收通过后再确定可发布的规模建议。桌面实测和真机判据见[成员 A 的渲染性能记录](../MEMBER_A_D10.md)。

## 5. 必须上报组长的阻断项

### 5.1 【已关闭】更新检查在鸿蒙构建下已编译关闭

**初稿结论有误，此处按实际构建配置更正。** 本节此前按 `leocad.pro` 推断「宏只在 macOS 定义、
鸿蒙可能未关自动更新、仓库无法核实」，据此定为 P0。核对实际的 CMake 构建后，这个结论不成立。

| 项 | 内容 |
|---|---|
| 实际构建入口 | `scripts/build-harmony-app.ps1` 用 `qt-cmake -S <仓库根>` 配置**根 CMake 工程**并产出 HAP，不走 `leocad.pro`。`leocad.pro` 是历史路径，不是鸿蒙构建路径 |
| 实际定义 | 根 `CMakeLists.txt:75–82` 对 `leocad` 目标**无条件**定义 `LC_DISABLE_UPDATE_CHECK=1`、`LC_DISABLE_RENDER_DIALOG=1`、`LC_DISABLE_BLENDER=1`；`if(OHOS)` 块内另加 `LC_DISABLE_NETWORK=1`、`LC_DISABLE_NON_CORE_FORMATS=1` |
| 编译证据 | 本机既有 Harmony 构建的 `qtmain.cpp` 编译命令包含 `LC_DISABLE_UPDATE_CHECK=1` 与 `LC_DISABLE_NETWORK=1`，即 `qtmain.cpp:308` 的 `#if !LC_DISABLE_UPDATE_CHECK` 分支在鸿蒙构建中**不参与编译** |
| 结论 | **自动更新检查在鸿蒙构建中已被编译关闭**，不会在首次启动访问 `leocad.org`。此前"宏只在 macOS 定义"的说法只对 qmake 路径成立，与鸿蒙实际构建无关 |
| 状态 | 该 P0 关闭。原判断基于读错构建系统，不是产品缺陷 |

**仍然成立、但性质不同的部分：网络权限清单需独立核对。**
「自动更新已关闭」只说明应用没有主动请求更新，**不等于**「全部离线声明已验收」：

- 隐私政策声称「不申请网络权限」，这是**包清单**层面的断言（`module.json5` 里有无 `ohos.permission.INTERNET`），
  与源码里的宏无关，必须查打包产物，不能由本节推断。
- `LC_DISABLE_NETWORK=1` 在 OHOS 下编译关闭网络层，是**双保险**（与 `ApplyFirstReleaseScope()`
  的菜单裁剪并存）；两者都成立才谈得上"离线"。
- 因此本节的验收项从「确认是否已传宏」改为「确认 HAP 清单未申请 INTERNET 权限 + 首次启动 hilog
  无 `leocad.org` 请求」，仍由组长在真机确认。

| 验证方法 | 真机首次启动（全新安装、清除数据）后抓 hilog，搜索 `leocad.org` / `updates.txt`：应无任何请求。同时解包 HAP 检查 `module.json5` 的 `requestPermissions` |
| 回归保护 | `scripts/library/test_network_scope.py` 现在解析根 CMakeLists 的 `target_compile_definitions`：删除 `LC_DISABLE_UPDATE_CHECK=1` 或 OHOS 下的 `LC_DISABLE_NETWORK=1` 都会使该测试失败（已做移除定义的负向验证） |

> 教训记在这里：审查构建约束要读**实际被调用的构建系统**，`leocad.pro` 与 `CMakeLists.txt` 在本仓库
> 并存且宏定义条件不同，只读其中一个会得出相反结论。

## 7. 性能边界

> 测量人：成员 C　测量日期：2026-11-05　原始数据与复现脚本：`docs/evidence/member-c/2026-11-05/performance/`
> 本节的所有数字**只来自桌面宿主**（WSL2 x86-64 + Qt 6.12 offscreen + debug 构建）。
> 真机数字一个都没有。凡写「未测」的地方，就是真的没有测量过，不是省略。

### 7.1 首发版的零件库规模：1160 件，不是完整 LDraw 库

首发包内是精简库 `assets/ldraw-lite/library-lite.zip`（3,833,541 字节，1160 件），不是官方完整
LDraw 库（库内实测口径为 24,985 件，见 `docs/D4_零件面板与库提示.md:173`）。这是**产品决策**，
见 §1 的 L-10，不是缺陷。

对性能的影响实测如下（1161 行，即清空筛选后的全部零件）：

| 项 | 实测 | 说明 |
|---|---|---|
| 零件库首次加载（空缓存） | 12.8–13.5 ms | 打开 zip + 建立描述索引，同时写入缓存索引文件。**探针显式传入 zip 路径，走普通文件读**；真机实测来源是 `:/assets/ldraw-lite/library-lite.zip`（qrc 内嵌，见 `docs/D4_DEVICE_ACCEPTANCE.md:75`），首次访问要先从 HAP 解压到内存，是探针**没有走**的路径 |
| 零件库再次加载 | 4.8–6.5 ms | 读缓存索引，不再解析每个零件文件 |
| 搜索框逐击键 | 0.20–0.62 ms（中位 0.27 ms） | 端到端：`setText` → 过滤 → 计数标签刷新 |

（1161 而不是 1160：`SetProject(new Project())` 会创建一个主模型，主模型自己也在库里注册了
一个占位 `PieceInfo`（`common/lc_model.cpp:287-294`），于是面板里多一行。这是真实运行状态，
不是探针多出来的行。真机 `LEOCAD_RESOURCE_PATHS.loaded_parts=1162` 是同一现象，
`docs/D5_DEVICE_ACCEPTANCE.md:57` 已记明「包含临时模型对象，不能当作正式精简库的零件数量」。）

结论：在 1160 件的规模下，零件面板的搜索与加载**都不构成用户可感知的延迟**。
用户输入一个字符的时间里（一次击键间隔通常 100 ms 以上），过滤只用了 0.27 ms。

### 7.2 首帧时间：宿主数字不能当真机数字用

桌面宿主上按 `lcApplication::Initialize()` 的真实顺序分段计时（3 轮）：

| 阶段 | 中位 | 备注 |
|---|---|---|
| `lcContext::InitializeRenderer()`（离屏 GL） | 180.7 ms | **占首启一半以上**，且是 offscreen 特有路径 |
| 样式 + 窗口 + 零件库 + 控件 + 工程 | 41.2 ms | 与渲染无关的纯 CPU 部分（含库 12.4 ms） |
| 以上合计 = `startup_before_show_ms` | 221.9 ms | `show()` 之前的一切 |
| `show()` 首次 | 111.6 ms（110.3–117.3） | offscreen 合成，不是 GPU 呈现 |
| **合计（首次启动到首帧）** | **333.5 ms**（322.1–344.8） | `startup_before_show` + 首次 `show()` |
| （参考）`show()` 之后各次 | 24.1 ms（22.6–30.3） | 重复 hide/show，不是启动，**不要计入首启** |

**这些数字不能作为真机首帧的预期值，原因有三：**

1. **offscreen 平台没有真实 GPU 呈现。** `show()` 那 110 ms 与 `InitializeRenderer()` 的 180 ms
   属于同一类开销：Mesa 在离屏表面上的初始化与软件合成。真机上这条路径由鸿蒙的 GPU 合成器
   承担，代码路径与耗时量级都不同。
2. **I/O 与 CPU 差异大。** 冷加载 13 ms 是 x86 + SSD + 页面缓存已热的结果；鸿蒙真机是 ARM64 + UFS。
   更关键的是取库路径不同：探针显式传入 zip 路径，而真机由 `lcPiecesLibrary::FindBundledLibraryArchive()`
   按候选顺序找库（`common/lc_library.cpp:260-283`，应用数据目录 → 二进制旁 → qrc 内嵌）。
   qrc 内嵌时首次访问要从 HAP 里解压到内存，那是一条探针没走的路径。两者不能换算，也不能互相验证。
3. **debug 构建。** 本轮测量用的是 `CONFIG+=debug`，未开优化；release 会更快。
   所以宿主数字既不是上限也不是下限，只能用来判断「哪个阶段值得关注」。

**真机首帧时间未测，由组长在 D10 真机 30 分钟稳定性测试中采集。** 采集时应记录：

| 采集项 | 方法 |
|---|---|
| 冷启动首帧（全新安装、清除数据后） | hilog 时间戳从 Ability 创建到首帧 `onDraw`；或外部录屏逐帧 |
| 二次启动首帧 | 同上，应用已在后台或被杀死后重启 |
| 零件面板首次可交互时间 | 点击搜索框到可以输入、列表已填充 |
| 稳定性对照 | 与 §4 的 V-06（30 分钟内存曲线）同一次会话采集 |

方案文档 D10 要求「定义可接受模型规模」，**该定义属成员 A**（渲染侧，含首帧、重绘、资源上传）。

### 7.4 已知限制：零件面板的过滤复杂度是 O(n) 每击键

这是一个**首发版不受影响、但会约束后续扩库**的实现限制，写入发布说明是为了让它将来被想起来。

`lcPartSelectionListModel::SetFilter()`（`common/lc_partselectionwidget.cpp:297-322`）对**每一行**
调用 `mListView->setRowHidden()`；随后 `lcPartSelectionWidget::RefreshStatus()`
（`common/lc_partselectionwidget.cpp:1670-1672`）为了刷新计数标签，又**完整扫一遍**所有行。
因此每次击键是两趟 O(n)。

实测增长（用 `SetCustomParts()` 把同一份 `SetFilter()` 指向更大的行数，非真实库，只测每行成本）：

| 行数 | 单次 `SetFilter()` |
|---|---|
| 1,160 | 0.25–0.28 ms |
| 5,000 | 1.1–1.4 ms |
| 20,000 | 4.7–5.7 ms |
| 50,000 | 13.3–17.9 ms |
| 100,000 | 41.9–46.8 ms |

近似线性：1160 行时约 0.23 µs/行，10 万行时约 0.44 µs/行，每行成本随规模略升。映射到实际场景：

| 场景 | 预计单次击键 | 用户是否可感知 |
|---|---|---|
| 首发版（1,160 件） | 0.27 ms | 完全无感 |
| 换成官方完整 LDraw 库（24,985 件） | 约 5–6 ms（20,000 行实测 4.7–5.7 ms） | 仍不可感知，但已进入「大量输入时可能有轻微掉帧」的量级 |
| 数万件以上 + 慢速 CPU | 15 ms 以上 | 可以感知到输入滞后 |

**首发版不做优化。** 在 1160 件的规模下这条路径不需要优化，为了「做点什么」而改它是本仓库禁止的行为；
也没有任何优化前后的对照数据可以报告，所以本节不含任何「提升 X%」的说法。

如果后续版本要扩充零件库，需要同时处理这两处 O(n)：把可见性判断与计数合并成一次遍历，
或改用 `QSortFilterProxyModel` 让视图只处理可见行。这两处改动都属**后续版本**范围。
