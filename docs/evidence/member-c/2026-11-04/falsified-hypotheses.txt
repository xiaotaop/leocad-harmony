D9：两条被实测证伪的"缺陷"怀疑（本轮未为此改任何代码）

这两条在 D8 收尾时被列为待办。关闭方式有两种：修掉，或者证明它不成立。
下面记录的是证明不成立的过程与输出。

--------------------------------------------------------------------
1) 双分隔线 / 前导分隔线：不是绘制出来的
--------------------------------------------------------------------
现象（只看动作列表）:
  File 菜单: ... Open / sep / Save... / sep / sep / Recent ...
              ^^^^^^^^^^^^^^^ 两条相邻分隔线
  Help 菜单: sep / About
              ^^^ 前导分隔线

怀疑: 首发范围裁剪删掉中间条目后，留下相邻/前导分隔线没有收拾。

实测（在真实菜单上量几何，不是读 actions()）:
  leading separators actually drawn:  0
  adjacent separators actually drawn: 0
  Help 的首条分隔线几何: sep(0x0)

原因: QMenu::separatorsCollapsible 默认就是 true。相邻分隔线在布局时
      合并，前导/尾随分隔线折叠成 0x0。用户在屏幕上看到的数量是对的。

结论: 不是缺陷，不改代码。也不应把"actions() 里有多余条目"写成缺陷。
      这解释了为什么 D3/D8 三轮真机验收都没人报过它。

补充（为什么尾随分隔线仍然要删）:
  尾随分隔线不会被折叠成 0x0，会在菜单底部留一条可见短线，
  所以 ApplyFirstReleaseScope() 末尾那个只删尾随分隔线的循环是正确的克制，
  删前导/相邻反而是在改上游默认行为。

--------------------------------------------------------------------
2) 被裁剪命令的快捷键会不会仍然触发：不会
--------------------------------------------------------------------
担心: 首发范围只把动作 setVisible(false)/setEnabled(false)，动作对象仍在
      窗口上（CreateActions() 里 addAction() 过）。若隐藏动作的快捷键仍能
      触发，裁剪就只是视觉上的——按 Ctrl+F 还能开出"查找"对话框。

实测（QTest::keyClick 打到真实窗口）:
  visible + enabled  -> fired: 1   （对照组，证明探针本身有效）
  hidden  + enabled  -> fired: 0
  hidden  + disabled -> fired: 0

结论: 不成立，不改。裁剪在键盘路径上也是真的。

--------------------------------------------------------------------
方法学备注
--------------------------------------------------------------------
两条都是"读 actions() 得出怀疑 -> 测真实可观察行为 -> 怀疑不成立"。
第一版结论曾把"双分隔线"写成待修缺陷，是量了几何之后才推翻的。
凡涉及"用户看得见什么"，必须以绘制结果为准，动作列表不算证据。
