# D4 零件面板接入与空库/损坏库提示

> 负责人：成员 C　日期：2026-10-30（D4）
> 依据：[`docs/LeoCAD_鸿蒙PC首发版_两周分工与技术方案.md`](LeoCAD_鸿蒙PC首发版_两周分工与技术方案.md) §5（10/30 D4）
> 基线：`main@4548f110`
> D4 交付要求：零件分类、搜索和颜色控件接入精简库；准备空库/损坏库提示

本文记录 D4 的代码交付。D3 已完成精简库加载、归档校验和菜单裁剪
（见 [`D3_主程序接入.md`](D3_主程序接入.md)）；本阶段补齐面板在**异常状态**下的表现，
并修正一个桌面就能看到的默认状态缺陷。

## 1. 排查结论：哪些是真缺口

D4 的两项要求里，一半在 D3 已经完成，先确认清楚再动手：

| D4 要求 | 状态 | 依据 |
|---|---|---|
| 零件分类接入精简库 | **已可用** | `UpdateCategories()` 读 `gCategories`，而 `gCategories` 由 `Load()` 经 `lcLoadDefaultCategories()` 重建；分类表达式匹配的是已加载的精简库零件 |
| 零件搜索接入精简库 | **已可用** | `lcPartSelectionListModel::SetFilter()` 遍历的是 `mParts`，即当前分类下的精简库条目 |
| 颜色控件接入精简库 | **已可用** | `LoadColors()` 从精简库归档内 `ldraw/ldconfig.ldr` 取色，`gColorList` 供 `lcColorList` 绘制 |
| **空库/损坏库提示** | **缺口** | 校验失败只 `fprintf(stderr)`，真机上无人可见 |
| 面板默认状态 | **缺口（自查发现）** | 新建面板不选中任何分类，首屏是空列表 |

前三条不需要改代码。真正要做的是后两条，以及由它们暴露出的一个既有缺陷。

## 2. 缺陷一：面板首屏为空（自查发现）

`UpdateCategories()` 只**恢复**已存在的选中项，从不主动建立选择：

```cpp
// 修改前：CurrentItem 为 null 时，循环结束后什么都不选
if (CurrentItem)
    mCategoriesWidget->setCurrentItem(CurrentItem);
```

新建面板时 `mCategoriesWidget->currentItem()` 为 null，因此没有任何分类被选中，
`lcPartSelectionListView` 从未收到 `SetCategory()`，列表为空。

上游行为相同。但 D2 §6.2 的面板草图明确画出「分类: [全部 ▼]」且列表有内容，
而分工文档 §1.1 的核心闭环第 2 步是「从分类或搜索结果中选择常用零件」——
首屏空白会让用户以为库没加载。

**修复**：构造末尾选中 `mAllPartsCategoryItem`。

**为什么测试能抓到**：面板一构造完，计数标签就应当是 1160 而不是 0。这条断言在
修复前直接失败（见 §5 回归表）。

### 2.1 首屏最终显示的是 Brick，不是 All Parts

上一版本文声称「首屏显示 1160 件」，这是**错的**，评审已指出并复现。

`lcApplication::Initialize()` 在 `CreateWidgets()` 之后、`show()` 之前调用
`SetDefaultPart()`（`common/lc_application.cpp:1284`），把分类切到 **Brick**：

```cpp
gMainWindow->SetColorIndex(lcGetColorIndex(7));
gMainWindow->GetPartSelectionWidget()->SetDefaultPart();
```

这是上游既有行为，本 PR **保留不改**。因此真实首屏是 Brick 分类，计数约为 156，
不是全库 1160。

| 阶段 | 分类 | 计数 |
|---|---|---|
| `CreateWidgets()` 之后 | All Parts | 1160 |
| `SetDefaultPart()` 之后（用户实际看到） | **Brick** | **约 156** |

**为什么保留 Brick**：改为默认 All Parts 会改变上游的零件插入习惯（新建模型时
先选一个常用砖块，比在看全库更接近建模流程），属产品决策，不在本 PR 范围。

**本 PR 修复的仍然成立**：修复前首屏是**空列表**（没有分类被选中），修复后是
Brick 分类且**有内容**。差别在「空 vs 非空」，不是「Brick vs 全库」。

新增 `startupEndsOnTheBrickCategory` 用例复现真实启动序列（`CreateWidgets()` +
`SetDefaultPart()`），断言最终分类为 Brick 且计数非 0。

## 3. 缺陷二：库异常只有 stderr

D3 §3.3 记录了当时的决定：校验失败写 stderr、不弹窗，理由是「启动流程需要能
无人值守运行」。这个理由对**启动流程**成立，对**用户可见性**不成立：

- 真机上看不到 stderr；
- 用户的可见症状是「零件面板只有 128 件」，而不是任何错误；
- 桌面版 `LoadPartsLibrary()` 整体失败会弹 `QMessageBox`（`lc_application.cpp:970`），
  但**单个归档被拒**走不到那条路径——列表里还有内置 128 件库，加载"成功"。

### 3.1 传递路径

```
qtmain.cpp
  PlaceBundledLibraryArchive() 返回 Rejection
  → lcPiecesLibrary::SetBundledLibraryProblem(Rejection)      ← 新增，静态
  → （stderr 保留，供日志与 bug 报告）

lcMainWindow::CreateWidgets()
  → mPartSelectionWidget->SetLibraryProblem(GetBundledLibraryProblem())   ← 新增

lcPartSelectionWidget
  → mLibraryProblemLabel（横幅）+ mEmptyNotice（空态）+ mCountLabel（计数）
```

用**静态**成员而不是实例成员：校验发生在任何 `lcPiecesLibrary` 实例存在之前
（`PlaceBundledLibraryArchive()` 是静态函数），此时没有对象可以挂载状态。

### 3.2 三种空状态必须区分

面板"没有零件"有三个完全不同的原因，用户需要三种不同的说法：

| 原因 | 界面 | 用户该做什么 |
|---|---|---|
| 库被拒 / 找不到 | 顶部黄色横幅，**不显示**空态 | 重装应用 |
| 搜索无结果 | 空态覆盖层，文案提"搜索" | 换关键词或清空 |
| 分类本身为空（Sticker） | 空态覆盖层，文案提"分类" | 换分类 |

**关键约束**：库异常时**不能**同时显示空态。否则一个打包缺陷会被描述成
"没有匹配的零件，请尝试其它关键词"，把用户引到错误方向。

```cpp
const bool ShowEmpty = VisibleCount == 0 && mLibraryProblem.isEmpty();
```

这条判断是 §5 回归验证里专门验证过的（见第三条）。

### 3.3 空态是覆盖层，不是布局项

D2 §6.2 已记录：把空态加进布局会在它出现时把列表挤小。实现为
`mPartsWidget->viewport()` 的子控件，用事件过滤器跟随视口尺寸：

```cpp
mPartsWidget->viewport()->installEventFilter(this);
// ...
if (mEvents 是 Resize) PositionEmptyNotice();
```

跟随**视口**而不是监听本 widget 的 `resizeEvent`：拖动 splitter 时面板尺寸变化
与视口尺寸变化不相等。

两个实现细节值得记录，都踩过：

| 细节 | 现象 |
|---|---|
| 用 `isHidden()` 而非 `isVisible()` | 构造期祖先未显示，`isVisible()` 恒为 false，定位被跳过，覆盖层保持 100×30 默认尺寸 |
| 用 `resize()+move()` 而非 `setGeometry(rect())` | 后者同时设置位置，Qt 视为显式放置，后续不再跟随 |

### 3.4 横幅配色跟随主题

LeoCAD 有深色主题，`lcApplication::UpdateStyle()` 会切到 Fusion 并把窗口底色设成
接近黑（`QColor(49,52,55)`）、文字接近白。横幅若用固定浅色背景 + 继承来的浅色文字，
在深色主题下不可读。

因此不用样式表，改用调色板的 `ToolTipBase` / `ToolTipText` 一对角色——它们本来就是
为「内联提示」存在的，深色调色板也已显式覆盖这两个值。新增 `bannerFollowsTheTheme`
守住这一点：断言 `autoFillBackground`、样式表为空、两个颜色等于调色板对应角色。

### 3.5 文案：不把打包诊断给用户

横幅正文是「仅少量零件可用，使用其它零件的模型会缺件」，校验器的原始措辞
（`references a file`、`expected 1160`）放进 **tooltip**。理由：前者是用户能理解
并据以行动的，后者是给 bug 报告用的。

### 3.6 横幅只在最终结果真的降级时出现（评审 P2 修正）

上一版本无条件把包内归档的拒绝原因交给面板，**这是错的**，评审已指出并复现。

`LoadPartsLibrary()` 的顺序是：`LEOCAD_LIB` → 用户偏好 → 传入路径列表。前两者任一
成功就 `return`，根本不会尝试包内归档。所以「包内归档被拒」与「实际用了小库」是
两件事：

| 包内归档 | 实际加载 | 旧行为 | 现行为 |
|---|---|---|---|
| 被拒 | LEOCAD_LIB 的 1160 件精简库 | **错误显示缺件横幅** | 无横幅 |
| 被拒 | 内置 128 件兜底 | 显示横幅 | 显示横幅 |
| 被拒 | 完整 LDraw 库（24985 件） | **错误显示缺件横幅** | 无横幅 |
| 正常 | 精简库 1160 件 | 无横幅 | 无横幅 |

**修复**：`CreateWidgets()` 在 `LoadPartsLibrary()` **之后**执行，此时
`GetPieceCount()` 就是最终值。新增谓词 `lcPiecesLibrary::IsLibraryDegraded(
LoadedPieces, ExpectedParts)`，只有实际件数低于承诺值才降级。诊断照旧保留
（tooltip + stderr），只是不再单独决定横幅。

期望值提成常量 `lcPiecesLibrary::BundledLibraryParts = 1160`，启动校验与降级判定
共用，避免两处数字漂移。

新增两个用例：`rejectedBundleWithWorkingExternalLibraryIsHealthy`（诊断保留、
横幅隐藏）与 `degradedVerdictTracksTheLoadedCount`（谓词边界：1159/128/0 降级，
1160/4640 不降级）。

端到端复现（临时程序，验证后删除）：坏归档 + `LEOCAD_LIB=library-lite.zip` →
`loaded=true pieces=1160`、`banner hidden=true`、`degraded=false`、诊断仍在；
换成 `LEOCAD_LIB=library.zip`（128 件）→ 横幅出现、`degraded=true`。两个方向都验过。

### 3.7 计数与空态由模型统一通知（评审 P2 修正）

上一版只在 `QLineEdit::textChanged` 里刷新。但齿轮菜单的
`ToggleFileNameFilter` / `TogglePartDescriptionFilter` / `ToggleRegularExpressionFilter`
直接调模型的 `SetFilter()`，不经过那条路径。症状：搜索 `3001` 得到 4 条，切换
Part ID 匹配后实际可见 0 条，标签仍是 `Parts: 4`、空态也不出现。

**修复**：把刷新点移到 `lcPartSelectionListModel::SetFilter()` 末尾，发
`VisibleRowsChanged()` 信号，面板在构造函数里连接。理由是可见行集合只由
`SetFilter()` 决定，全文件共 14 处 `SetFilter(mFilterString)` 调用，逐个补槽必漏；
改成信号后，选项菜单、In Use、子模型、调色板、分类切换全部覆盖。

`FilterChanged()` 与 `CategoryChanged()` 里原有的两处 `RefreshStatus()` 已删除，
否则每次按键重复 recount 两遍。

新增 `optionToggleRefreshesCountAndEmptyState`：真实面板 + 真实模型，搜索 `3001`
后关闭两个匹配开关，断言可见行归 0、标签跟着变、空态出现。

### 3.8 两条提示只留一个判据（第二轮评审修正）

上一版把两个条件分开算，二者可能同时为假：

```
横幅显示  = Degraded && !Problem.isEmpty()
空态显示  = VisibleCount == 0 && !Degraded
```

`Problem` 为空且 `Degraded` 为真时，两条都不成立 → 列表空、`Parts: 0`、
**没有任何说明**。这个组合在真实路径上可达：包内精简库完好（没有可诊断的问题），
而 `LEOCAD_LIB` 指向一个有效但很小的库（如 `resources/library.zip`，128 件），
加载成功但件数不足。

**修复**：

- 横幅改为只要降级就显示。降级本身就该说明；有诊断就放进 tooltip，没有就不放。
  「解释不了」不该变成「什么都不说」。
- 空态抑制改为读**横幅自身是否在显示**（`isHidden()`），不再重算 `mLibraryDegraded`。
  两条判据从此不可能分叉。

用 `isHidden()` 而非 `isVisible()`：后者在祖先隐藏时也为 false，窗口显示前会把
横幅误判成「没在解释」，空态于是漏出。

新增 `degradedWithoutDiagnosticStillExplainsAnEmptyList` 覆盖
`(Problem 空, Degraded true)`：横幅出现；列表为空时两者至少有一个在说明。

端到端复现（临时进程，验证后删除）：`LEOCAD_LIB=resources/library.zip` →
加载 128 件、`degraded=true`、横幅显示、空态隐藏、`explained=true`。
同时套用两条旧判据 → 横幅与空态都隐藏、`explained=false`，即评审报的状态。

计数标签按当前**可见**条目计数，所以筛选时它同时告诉用户"匹配了多少"。

用 `tr("Parts: %1")` 而不是 `tr("%n part(s)", ...)`：复数形式只有在提供翻译、
且翻译带复数规则后才读得通，而这条串目前尚未翻译（已知问题 F-02）。未翻译时
`%n` 会原样渲染成字面的 "part(s)"，比回避复数更糟。

## 4. 分类与颜色确实来自精简库

不是靠读代码推断，而是 D3 的真机证据已经覆盖：`curated-device.mpd` 使用了内置
128 件库没有的 `10172.dat` 与 `30293.dat`，真机显示真实几何而非占位方块
（见 [`D3_RESOURCES_DEVICE_ACCEPTANCE.md`](D3_RESOURCES_DEVICE_ACCEPTANCE.md)）。
能渲染出这两个零件，说明 `mPieces` 里就是精简库；分类树与颜色表都由同一份
`Load()` 结果构建。

本阶段新增的桌面断言固定了 All Parts 分类下的计数为 1160（`countShowsVisibleParts`），
真实首屏的分类与计数见 §2.1。

## 5. 自动化测试（新增 15 项）

新增套件 `tests/library/d4/tst_parts_panel.cpp`，工程 `d4-panel-tests.pro`，

### 回归验证

每条断言都实际改坏并确认失败：

| 改坏的行为 | 失败项数 | 报错 |
|---|---:|---|
| 去掉构造末尾的 All Parts 选择 | 2 | 计数停在 `Parts: 0` |
| 去掉 `VisibleRowsChanged()` 信号 | 5 | `Parts: 0 vs 4 visible`，空态不出现 |
| 恢复「只看包内归档是否被拒」的横幅判据 | 1 | 正常外部库仍显示缺件横幅 |
| 把 `startupEndsOnTheBrickCategory` 的期望改成 All Parts | 1 | 与实际启动序列不符 |
| 横幅重新要求非空诊断 | 1 | 无诊断的降级不显示横幅 |
| `SetLibraryProblem()` 提前返回 | 5 | 横幅与空态均不出现 |
| 空态忽略 `mLibraryProblem` | 1 | 库损坏时提示"没有匹配的零件" |
| 横幅不走调色板（去掉 `setPalette`） | 1 | 背景不是主题的提示色 |

第三条第一次改坏时**没有失败**——因为库正常时列表非空，`VisibleCount == 0`
不成立，那段代码根本没执行到。用例补上"先搜索到空、再设库异常"之后才真正生效。
这是本轮第二个假通过，与 D3 的 priority 套件同类：断言的条件在实际场景里不成立。

## 8. 待真机确认

以下项目**本阶段不验收**，需组长在下一批真机确认：
