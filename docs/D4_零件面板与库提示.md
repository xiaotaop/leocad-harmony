# D4 零件面板接入与空库/损坏库提示

> 负责人：成员 C　日期：2026-10-30（D4）
> 依据：[`docs/LeoCAD_鸿蒙PC首发版_两周分工与技术方案.md`](LeoCAD_鸿蒙PC首发版_两周分工与技术方案.md) §5（10/30 D4）
> 基线：`main@4548f110`
> D4 交付要求：零件分类、搜索和颜色控件接入精简库；准备空库/损坏库提示

本文记录 D4 的代码交付。D3 已完成精简库加载、归档校验和菜单裁剪
（见 [`D3_主程序接入.md`](D3_主程序接入.md)）；本阶段补齐面板在**异常状态**下的表现，
并修正一个桌面就能看到的默认状态缺陷。

## 1. 排查结论：哪些是真缺口

D4 的两项要求里，一半在 D3 已经完成，先确认清楚再动手：

| D4 要求 | 状态 | 依据 |
|---|---|---|
| 零件分类接入精简库 | **已可用** | `UpdateCategories()` 读 `gCategories`，而 `gCategories` 由 `Load()` 经 `lcLoadDefaultCategories()` 重建；分类表达式匹配的是已加载的精简库零件 |
| 零件搜索接入精简库 | **已可用** | `lcPartSelectionListModel::SetFilter()` 遍历的是 `mParts`，即当前分类下的精简库条目 |
| 颜色控件接入精简库 | **已可用** | `LoadColors()` 从精简库归档内 `ldraw/ldconfig.ldr` 取色，`gColorList` 供 `lcColorList` 绘制 |
| **空库/损坏库提示** | **缺口** | 校验失败只 `fprintf(stderr)`，真机上无人可见 |
| 面板默认状态 | **缺口（自查发现）** | 新建面板不选中任何分类，首屏是空列表 |

前三条不需要改代码。真正要做的是后两条，以及由它们暴露出的一个既有缺陷。

## 2. 缺陷一：面板首屏为空（自查发现）

`UpdateCategories()` 只**恢复**已存在的选中项，从不主动建立选择：

```cpp
// 修改前：CurrentItem 为 null 时，循环结束后什么都不选
if (CurrentItem)
    mCategoriesWidget->setCurrentItem(CurrentItem);
```

新建面板时 `mCategoriesWidget->currentItem()` 为 null，因此没有任何分类被选中，
`lcPartSelectionListView` 从未收到 `SetCategory()`，列表为空。

上游行为相同。但 D2 §6.2 的面板草图明确画出「分类: [全部 ▼]」且列表有内容，
而分工文档 §1.1 的核心闭环第 2 步是「从分类或搜索结果中选择常用零件」——
首屏空白会让用户以为库没加载。

**修复**：构造末尾选中 `mAllPartsCategoryItem`。

**为什么测试能抓到**：面板一构造完，计数标签就应当是 1160 而不是 0。这条断言在
修复前直接失败（见 §5 回归表）。

## 3. 缺陷二：库异常只有 stderr

D3 §3.3 记录了当时的决定：校验失败写 stderr、不弹窗，理由是「启动流程需要能
无人值守运行」。这个理由对**启动流程**成立，对**用户可见性**不成立：

- 真机上看不到 stderr；
- 用户的可见症状是「零件面板只有 128 件」，而不是任何错误；
- 桌面版 `LoadPartsLibrary()` 整体失败会弹 `QMessageBox`（`lc_application.cpp:970`），
  但**单个归档被拒**走不到那条路径——列表里还有内置 128 件库，加载"成功"。

### 3.1 传递路径

```
qtmain.cpp
  PlaceBundledLibraryArchive() 返回 Rejection
  → lcPiecesLibrary::SetBundledLibraryProblem(Rejection)      ← 新增，静态
  → （stderr 保留，供日志与 bug 报告）

lcMainWindow::CreateWidgets()
  → mPartSelectionWidget->SetLibraryProblem(GetBundledLibraryProblem())   ← 新增

lcPartSelectionWidget
  → mLibraryProblemLabel（横幅）+ mEmptyNotice（空态）+ mCountLabel（计数）
```

用**静态**成员而不是实例成员：校验发生在任何 `lcPiecesLibrary` 实例存在之前
（`PlaceBundledLibraryArchive()` 是静态函数），此时没有对象可以挂载状态。

### 3.2 三种空状态必须区分

面板"没有零件"有三个完全不同的原因，用户需要三种不同的说法：

| 原因 | 界面 | 用户该做什么 |
|---|---|---|
| 库被拒 / 找不到 | 顶部黄色横幅，**不显示**空态 | 重装应用 |
| 搜索无结果 | 空态覆盖层，文案提"搜索" | 换关键词或清空 |
| 分类本身为空（Sticker） | 空态覆盖层，文案提"分类" | 换分类 |

**关键约束**：库异常时**不能**同时显示空态。否则一个打包缺陷会被描述成
"没有匹配的零件，请尝试其它关键词"，把用户引到错误方向。

```cpp
const bool ShowEmpty = VisibleCount == 0 && mLibraryProblem.isEmpty();
```

这条判断是 §5 回归验证里专门验证过的（见第三条）。

### 3.3 空态是覆盖层，不是布局项

D2 §6.2 已记录：把空态加进布局会在它出现时把列表挤小。实现为
`mPartsWidget->viewport()` 的子控件，用事件过滤器跟随视口尺寸：

```cpp
mPartsWidget->viewport()->installEventFilter(this);
// ...
if (mEvents 是 Resize) PositionEmptyNotice();
```

跟随**视口**而不是监听本 widget 的 `resizeEvent`：拖动 splitter 时面板尺寸变化
与视口尺寸变化不相等。

两个实现细节值得记录，都踩过：

| 细节 | 现象 |
|---|---|
| 用 `isHidden()` 而非 `isVisible()` | 构造期祖先未显示，`isVisible()` 恒为 false，定位被跳过，覆盖层保持 100×30 默认尺寸 |
| 用 `resize()+move()` 而非 `setGeometry(rect())` | 后者同时设置位置，Qt 视为显式放置，后续不再跟随 |

### 3.4 横幅配色跟随主题

LeoCAD 有深色主题，`lcApplication::UpdateStyle()` 会切到 Fusion 并把窗口底色设成
接近黑（`QColor(49,52,55)`）、文字接近白。横幅若用固定浅色背景 + 继承来的浅色文字，
在深色主题下不可读。

因此不用样式表，改用调色板的 `ToolTipBase` / `ToolTipText` 一对角色——它们本来就是
为「内联提示」存在的，深色调色板也已显式覆盖这两个值。新增 `bannerFollowsTheTheme`
守住这一点：断言 `autoFillBackground`、样式表为空、两个颜色等于调色板对应角色。

### 3.5 文案：不把打包诊断给用户

横幅正文是「内置零件库无法加载，仅少量零件可用；使用其它零件的模型会缺件」，
校验器的原始措辞（`references a file`、`expected 1160`）放进 **tooltip**。
理由：前者是用户能理解并据以行动的，后者是给 bug 报告用的。

计数标签用 `tr("%n part(s)", "", VisibleCount)`，按当前**可见**条目计数，
所以筛选时它同时告诉用户"匹配了多少"。

## 4. 分类与颜色确实来自精简库

不是靠读代码推断，而是 D3 的真机证据已经覆盖：`curated-device.mpd` 使用了内置
128 件库没有的 `10172.dat` 与 `30293.dat`，真机显示真实几何而非占位方块
（见 [`D3_RESOURCES_DEVICE_ACCEPTANCE.md`](D3_RESOURCES_DEVICE_ACCEPTANCE.md)）。
能渲染出这两个零件，说明 `mPieces` 里就是精简库；分类树与颜色表都由同一份
`Load()` 结果构建。

本阶段新增的桌面断言进一步固定了数字：面板计数必须是 1160。

## 5. 自动化测试（新增 10 项）

新增套件 `tests/library/d4/tst_parts_panel.cpp`，工程 `d4-panel-tests.pro`，
已接入 `scripts/dev/run-d3-tests.sh` 与 `scripts/Run-D3Tests.ps1`（套件名 `panel`）。

| 用例 | 断言 |
|---|---|
| `countShowsVisibleParts` | 构造完计数为 1160 |
| `healthyLibraryShowsNoBanner` | 健康安装无横幅 |
| `refusedLibraryShowsBannerAndTooltip` | 横幅出现；正文不含内部措辞；tooltip 保留原文 |
| `refusedLibraryDoesNotBlameTheFilter` | 库异常 + 列表空时，空态**不**出现 |
| `filterWithNoMatchShowsSearchNotice` | 搜索无结果时提"搜索"，计数归 0，清空后消失 |
| `emptyCategoryShowsCategoryNotice` | Sticker 空分类提"分类"，不提"搜索" |
| `emptyNoticeCoversViewportNotLayout` | 覆盖层父对象是 viewport 且尺寸一致 |
| `bannerFollowsTheTheme` | 横幅取调色板的 ToolTip 配色，不用固定色与样式表 |

### 回归验证

每条断言都实际改坏并确认失败：

| 改坏的行为 | 失败项数 | 报错 |
|---|---:|---|
| 去掉构造末尾的 All Parts 选择 | 2 | `0 part(s)` |
| `SetLibraryProblem()` 提前返回 | 5 | 横幅与空态均不出现 |
| 空态忽略 `mLibraryProblem` | 1 | 库损坏时提示"没有匹配的零件" |
| 横幅不走调色板（去掉 `setPalette`） | 1 | 背景不是主题的提示色 |

第三条第一次改坏时**没有失败**——因为库正常时列表非空，`VisibleCount == 0`
不成立，那段代码根本没执行到。用例补上"先搜索到空、再设库异常"之后才真正生效。
这是本轮第二个假通过，与 D3 的 priority 套件同类：断言的条件在实际场景里不成立。
