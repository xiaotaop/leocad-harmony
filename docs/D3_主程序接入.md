## 2. 精简库接入

### 2.1 携带方式

`assets/ldraw-lite/library-lite.zip`（3.7 MB）以 qrc 别名编译进二进制：

```xml
<file alias="assets/ldraw-lite/library-lite.zip">assets/ldraw-lite/library-lite.zip</file>
```

选 qrc 而非首启解压的理由见 D2 §4.2：库与程序同版本、无写权限依赖、规避鸿蒙沙箱
私有目录的权限路径问题。

### 2.2 三级探测

`lcPiecesLibrary::GetBundledLibraryArchiveCandidates()` 按序返回：

| 顺序 | 位置 | 用途 |
|---:|---|---|
| 1 | `QStandardPaths::AppLocalDataLocation` | 平台层首启展开到可写目录 |
| 2 | `applicationDirPath()` | 桌面版随包分发、开发调试 |
| 3 | `:/assets/ldraw-lite/library-lite.zip` | qrc 内嵌，兜底 |

`FindBundledLibraryArchive()` 返回第一个存在的路径。

### 2.3 接入位置与优先级

`qt/qtmain.cpp` 在 `Application.Initialize(LibraryPaths)` 之前插入：

```cpp
const QString BundledLibrary = lcPiecesLibrary::FindBundledLibraryArchive();
if (!BundledLibrary.isEmpty()) { /* 校验通过后 */ LibraryPaths.prepend(qMakePair(BundledLibrary, true)); }
```

标 `true` 表示官方库，使 `lcPiecesLibrary::SetOfficialPieces()` 记录件数。

**必须 prepend，不能 append。** `LoadPartsLibrary()` 在第一个 `Load()` 成功的路径上
立即返回，而列表里的「包内副本」不止一个：

| 来源 | 加入方式 | 件数 |
|---|---|---:|
| 精简库（本方案） | `prepend` | 1160 |
| HarmonyOS `:/resources/library.zip`（组长 PR #11） | `+=`，且最先加入 | 128 |
| 平台 `library.bin` | `+=` | — |

若用 `+=`，精简库排在末尾，**鸿蒙主程序会选中 128 件库，且没有任何报错**。
与 PR #11 的三方合并是文本干净的，所以这属于**语义集成冲突**，只能靠约定与
回归测试守住：`tst_library_priority.cpp` 构造竞争列表，断言精简库排在首位，
并按零件名核对（`10172` 只存在于精简库），不只看件数。

**不覆盖用户显式配置**：`LEOCAD_LIB` 与「零件库」偏好由 `LoadPartsLibrary()`
在遍历列表之前检查，仍最优先。

## 3. 显式校验（本阶段的核心修正）

### 3.1 为什么不能只看返回值

D2 §4.1 已核实加载器的实际行为：

```cpp
// common/lc_library.cpp:442 —— 根目录不对的条目被跳过，不中断
if (memcmp(Name, "LDRAW/", 6))
    continue;
// ...
// :486
return true;               // 循环结束后无条件返回成功
```

由此得出的结论是确定的：**根目录错误、ldconfig.ldr 缺失、引用断裂，三种情况
`Load()` 都返回 `true`**。应用表现为「零件库加载成功、零件数 0 或颜色错误、
面板空白」，且没有任何错误输出。

所以备用库的触发条件不能是 `Load() == false`，必须在加载前独立检查。

### 3.2 四项检查

`ValidateBundledLibraryArchive(FileName, ExpectedParts)` 在加载前直接扫描归档：

| # | 检查 | 判据 | 不通过时的症状（若不检查） |
|---:|---|---|---|
| 1 | 目录结构 | 每个条目都以 `ldraw/` 开头 | 条目全部被跳过，看似成功 |
| 2 | 关键文件 | `ldraw/ldconfig.ldr` 存在、可读、**至少解析出一条有效颜色**（有 CODE 与 VALUE） | 颜色**静默**回落内置色表 |
| 3 | 零件数量 | 顶层零件数 == 1160 | 空库或残缺库上线 |
| 4 | 引用完整性 | 归档内每个文件的 `1` 行引用都能解析 | 模型缺件，且不报错 |

`ExpectedParts` 取自 `assets/ldraw-lite/manifest.json` 的 `counts.parts`，当前 1160。
传 0 可跳过数量检查。

第 4 项的语义边界：**只检查「归档里有的文件，其依赖是否也在归档里」**，不要求
闭包完整。用户若装了完整官方库，引用可以指向子集之外，那是合法的。「闭包是否
完整」由 `scripts/library/export_part_list.py` 在打包阶段回答。

第 2 项**必须校验内容，而且必须用真实解析器判断**，不能只看文件名，也不能只统计
`0 !COLOUR` 前缀。`LoadColors()` 在色表解析不出任何颜色时会静默回落到内置调色板，
所以一个「存在但为空」「存在但损坏」或「有指令外壳但没有数据」的 `ldconfig.ldr`
会让归档通过全部检查，然后让每个零件都显示错误颜色。

「有指令外壳但没有数据」是最隐蔽的一种：

```
0 !COLOUR Broken
```

这行有 `!COLOUR` 指令，但没有 `CODE` 也没有 `VALUE`。前缀扫描会把它计为 1 条颜色，
而真实解析器（`lcParseColorFile()` 的 `Color.Code == ~0U || Color.Value[0] == FLT_MAX`
判据）会丢弃它——文件实际产出 0 条颜色。

因此本实现**复用加载器自己的解析函数**，而不是另写一套文本判断：

```cpp
const std::vector<lcColor> Colours = lcParseColorFile(ConfigFile);
if (Colours.empty()) { /* 拒绝 */ }
```

**为什么能复用而不污染全局状态**：`lcParseColorFile()` 是 `lcLoadColorFile()` 的
无副作用前半段——它只构造一个局部 `std::vector`，不触碰 `gColorList`、
`gColorGroups`、`gDefaultColor`、`gEdgeColor`，也不读偏好设置。
`lcLoadColorFile()` 则相反：它写全局色表并调用 `lcAdjustStudStyleColors()`
（后者读 `lcGetPreferences()`），所以**不能**拿来做预校验。
这一点由 `validationDoesNotTouchGlobalColours` 守住。

拒绝的四种情况：

| 情况 | 诊断 |
|---|---|
| 无法读取 | `ldraw/ldconfig.ldr cannot be read` |
| 内容为空 | `ldraw/ldconfig.ldr is empty` |
| 有指令但无有效记录（`0 !COLOUR Broken`） | `no usable colour definitions` |
| 只有 `CODE` 没有 `VALUE` | `no usable colour definitions` |

### 3.3 失败回退

```
校验通过                          → prepend 到 LibraryPaths 最前，用精简库
找不到归档 / 校验不通过            → 不动列表，stderr 记录原因
                                     LoadPartsLibrary() 继续尝试平台路径
                                     仍失败则退到内置 resources/library.zip（128 件）
```

失败**不中止启动**。这是刻意的：精简库是可选优化，不是启动前提；退化为 128 件
可用，比启动失败好。

**回退档位的已知限制**（自查新增）：内置 `resources/library.zip` 里**没有
`ldconfig.ldr`**。它仍能加载——`LoadColors()` 提取不到色表时会落到
`lcLoadDefaultColors()`——所以退档不会崩溃、不会白屏，但颜色用的是 LeoCAD 内置
默认调色板，不是 LDraw 官方色值，与「1160 件 + 官方 ldconfig」的正常档位有可见
差异。

因此这条回退是**可用性兜底，不是等效替代**。真机上若看到零件颜色与预期不符，
先确认 `stderr` 有没有 `Bundled parts library rejected:`，而不是去查颜色面板。

错误写 stderr 而非弹窗：启动流程需要能无人值守运行，且这是打包缺陷，不是用户
可修复的错误。

### 3.4 桌面验证

三项坏归档实验，均使用合成归档，不依赖真机：

| 缺 ldconfig | 删 `ldraw/ldconfig.ldr` | 拒绝 |

## 4. 菜单裁剪

`lcMainWindow::ApplyFirstReleaseScope()` 在 `CreateMenus()` 末尾调用，移除 55 项命令
对应的 `QAction`。分组与依据见 D1 §3。

### 4.1 只摘 QAction，不动控件

**关键约束**：`UpdateDockWidgetActions()` 会无条件解引用
`mPartsToolBar`/`mColorsToolBar`/`mPropertiesToolBar`/`mTimelineToolBar`/
`mPreviewToolBar`。把这些指针置空会让下次打开「视图」菜单崩溃。因此只从菜单与
工具栏移除 `QAction`，动作对象与 dock 指针全部保留。

### 4.2 子模型：保留标签栏，只收窄结构修改

按 D1 §1.3 结论，标签栏是 MPD 子模型的唯一可视载体，隐藏它等于把最常用的导航
藏进两层菜单。所以保留可见，只去掉三种改结构的方式：

| 项 | 设置 | 原因 |
|---|---|---|
| `setMovable()` | `false` | 拖动标签 = 重排子模型 |
| `setTabsClosable()` | `false` | 关最后一个标签会调用 `NewProject()` |
| `setContextMenuPolicy()` | `NoContextMenu` | 标签菜单含重命名/删除/新建 |
| `LC_MODEL_LIST` | **保留** | 同一动作的第二个入口 |

`setTabsClosable(false)` 的直接依据（已在 `main` 上核实）：

```cpp
// common/lc_mainwindow.cpp:1073
void lcMainWindow::ModelTabClosed(int Index)
{
    if (mModelTabWidget->count() != 1)
        delete mModelTabWidget->widget(Index);
    else
        NewProject();     // 关掉最后一个标签 → 新建工程，不是空白状态
}
```

这三项设置**必须在 `CreateWidgets()` 里做**，不能放进 `ApplyFirstReleaseScope()`：
后者由 `CreateMenus()` 调用，而 `CreateMenus()` 在 `CreateWidgets()` 内部、
`mModelTabWidget` 构造之前执行。

### 4.3 与成员 B 的隔离互补

成员 B 的 PR #10 让 `Project` 的非核心导出在 `LC_DISABLE_NON_CORE_FORMATS` 下返回
错误；本阶段把对应菜单项摘掉。两者是不同层：

- 菜单摘掉 → 用户不再被引到一个只能失败的对话框；
- API 拒绝 → 即使通过快捷键、命令行或将来的入口触达，也不会写文件。

`LC_MODEL_LIST` 在两边的处理不同是刻意的：B 管数据面（不改 MPD 结构），C 管界面
（保留切换入口）。

### 4.4 空子菜单（D4 补修，组长真机反馈）

真机验收发现文件菜单里仍有「导入」「导出」两个分组，与交接清单「看不到导出项」
不符，见 [`D3_RESOURCES_DEVICE_ACCEPTANCE.md`](D3_RESOURCES_DEVICE_ACCEPTANCE.md)。

**原因**：`CreateMenus()` 用 `FileMenu->addMenu(tr("&Import"))` 建容器，
`ApplyFirstReleaseScope()` 只摘 `QAction`，不摘容器。分组里的条目全部不可见之后，
`QMenu` 本身仍是父菜单里的一个可见项，点开是一个空框。

**为什么测试没抓到**：`tst_menu_scope.cpp` 只断言「命令不可见」，而空容器的条目
恰恰**全部不可见**——测试断言的正是缺陷的表现。这与此前 priority 套件的假通过同属
一类：断言了症状，没断言用户看到的界面。

**修复**（`lc_mainwindow.cpp`）：摘除动作时记录受影响的父菜单，之后对每个父菜单
检查「除分隔符外是否还有可见条目」，没有则连 `menuAction()` 一起摘掉。三处细节：

| 细节 | 为什么 |
|---|---|
| 只看**被摘过的**父菜单 | 全窗口扫描会误伤「构造时为空、`aboutToShow` 时填充」的菜单。目前没有这种菜单，规则先立住 |
| 空 = 无可见非分隔符条目，不是 `actions().isEmpty()` | Step 菜单两组之间留着一个分隔符，对用户是空的，但 `actions()` 非空 |
| 只摘 `menuAction()`，不 delete `QMenu` | 容器是窗口子对象，摘掉父项后没人再引用它；删除反而要处理析构顺序 |

**实测结果**（无显示环境遍历菜单栏可达的菜单树）：

| 菜单 | 修复前 | 修复后 |
|---|---|---|
| 文件 | `[&Import] 0`、`[&Export] 0` | 均不出现 |
| 视图 | `[Ste&p] 0` | 不出现 |
| 文件 | `[&Render]`（`LC_DISABLE_RENDER_DIALOG` 下本就不建） | 不出现 |

新增 `noVisibleEmptySubmenus` 用例，从菜单栏**向下遍历可达菜单**（不是
`findChildren<QMenu*>()`——那会把从没挂上菜单栏的菜单也算进来），断言每个可达菜单
至少有一个可见的非分隔符条目。套件由 7 项增至 8 项。

**回归验证**：注释掉修复段复跑，用例报出
`submenus with no visible entry: &Import, &Export, &Render, Ste&p` 并失败；
恢复后 8/8 通过。

**顺带确认的一件非缺陷**：File/Edit/View/Piece 里仍有相邻的 `---`。Qt 在布局时会把
相邻、开头、结尾的分隔符折叠成 0 高度（已用最小程序实测：两个连续 separator 中第二个
`actionGeometry()` 为空、高度 0），屏幕上不出现多余横线。本阶段**没有**为它加断言
——那会是一条永远为真或永远为假的测试。

### 4.5 时间线面板的 step 命令（D4 补修）

**问题**：`ApplyFirstReleaseScope()` 移除了菜单里的 `LC_VIEW_TIME_*`，但时间线面板的
右键菜单挂的是**另一套命令 ID**——`common/lc_timelinewidget.cpp` 的
`CustomMenuRequested()` 直接 `addAction(gMainWindow->mActions[LC_TIMELINE_*])`：

| 命令 | 标签 |
|---|---|
| `LC_TIMELINE_SET_CURRENT` | Set Current Step |
| `LC_TIMELINE_INSERT_BEFORE` / `_AFTER` | Insert Step Before / After |
| `LC_TIMELINE_DELETE` | Remove Step |
| `LC_TIMELINE_MOVE_SELECTION` / `_BEFORE` / `_AFTER` | Move Selection Here / Before / After |

这 7 项全部对用户可点，且操作的是同一批步骤——正是首发范围要排除的「步骤编辑」。
时间线面板经 `tabifyDockWidget(mPropertiesToolBar, mTimelineToolBar)` 与属性面板并列，
默认存在，右键即可触达。

**为什么一直没被发现**：两套命令做同一件事、却是两套 ID。菜单那套被移除后，从菜单
路径看起来「步骤功能已经没了」。

**本次修复（最小改动）**：把 7 个 `LC_TIMELINE_*` 加入 `RemovedCommands[]`。数组由
48 项增至 **55** 项。

**为什么只做这一步**：隐藏整个时间线面板属于产品决策（面板同时用于查看步骤结构），
不是纯缺陷修复，需要另行确认。当前处理是「按钮还在、点了无效」，堵住的是改文档结构
这个实质风险。

**已知副作用**：`lc_mainwindow.cpp` 的 `UpdateSelectionUI()` 仍会调用
`mActions[LC_TIMELINE_MOVE_SELECTION*]->setEnabled()`。`setEnabled()` 只改 enabled、
不影响 visibility，所以那三个动作不会因此重新出现在菜单里，但这段调用现在是无意义的
（对已移除的动作设 enabled）。留着不影响行为，删除需另开改动。

**新增断言**：`removedCommandsAreNotVisible` 的抽查清单加入全部 7 项。

**回归验证**：把这 7 行从数组删掉后复跑，用例失败并报
`Set Current Step is still visible in a menu`；恢复后 8/8 通过。

**未覆盖**：`createPopupMenu()`（工具栏右键菜单）在弹出时才构建，
`ApplyFirstReleaseScope()` 执行时它还不存在，因此对它的移除无效。本次未处理——
它列的是工具栏开关，不是步骤编辑命令，不属同一风险。

## 5. 图标与面板资源

```cpp
QIcon ApplicationIcon;

                              ":/resources/leocad-256.png",
                              ":/resources/leocad-512.png" })
    /* 逐尺寸 addPixmap，加载失败的尺寸跳过 */ ;
```

`:/resources/leocad.png` 这个别名保留（仍指向 64x64），避免其他调用方失效。
