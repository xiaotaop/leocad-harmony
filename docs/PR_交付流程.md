# 分支自证完成后再发起 PR

组长 2026-11-03 指示：**之后的开发先在分支上确认完成，再发起 PR**。

> 基线说明：本文堆叠在 **PR #48** 之上（分支 `feature/c-d8-interface-freeze`，head `53c08ba7`），
> 因此文中引用的 `scripts/library/test_packaged_resources.py`、runner 的 `FAIL!` 回显修复、
> 以及 `tst_menu_scope.cpp` 的新断言都在 #48 里。**#48 合并前本文单独检出会指到不存在的文件**，
> 请按依赖顺序评审合并。这本身就是 §1 规则第 1 条的一次现场执行：先确认分支状态自证得起来，再发 PR。
本文把这条规则写成可执行的清单，依据是本轮 D8（PR #48）里实际发生的事——包括三次由 CI 而不是我自己抓出的错误。

## 1. 规则

1. 分支进入「可评审」状态之前，先在本章 §2 的清单上自证完成；未过清单不发 PR。
2. 已经开了 PR 之后，**不在 PR 上连续推送**：攒够一个完整、自证过的变更集再推一次。
   本仓库 `continuous.yml:16-18` 与 `model-ci.yml:13-15` 均为 `cancel-in-progress: true`，
   同一 PR 的重复推送会取消进行中的那一轮——**攒批推送才是省 CI**，随手推送等于把已跑的轮次作废。
3. 文档/注释类改动不豁免清单：本轮错误结论**全部**出在文档与 issue 评论上，与代码无关。

## 2. 分支自证清单

清单按变更作用域分层，否则「改一行注释也要跑 20 分钟全量」会很快被人绕过：

- **触及代码 / 构建脚本 / CI 的分支**：下表全部执行。
- **纯文档分支**：执行「空白与尾随」+ §3 的准确性核对（每个被引用的行号、文件名、测试名都要实地验证），
  并在 PR 里写明「相对 main 无代码差异」——`main` 自身的 CI 已是绿的，全量重跑不产生新信息。
- **纯测试分支**：下表全部执行，并额外做负向验证（检查必须能因撤回被测改动而失败）。

| 项 | 命令 / 做法 | 本轮对应事实 |
|---|---|---|
| 全量套件 | `bash scripts/dev/run-d3-tests.sh` | 10 套件 112 项，0 失败 0 跳过 |
| 静态检查 | `python3 scripts/library/test_*.py` | 23 项（10 + 8 + 5） |
| 翻译可编译 | `lrelease resources/leocad_zh_CN.ts -qm /tmp/x.qm` | 1891 finished / 0 unfinished |
| 空白与尾随 | `git diff --check` | 干净 |
| **干净检出模拟** | 把构建产物移走后再跑检查 | 见 §3.1 |
| **负向验证** | 主动把修复撤回，确认检查**因此**失败 | 帮助菜单裁剪、图标死引用、`.ts` 追溯三处都做了 |
| 结论回到代码 | 文档/评论里每个「已修 / 未修」都去读实现与现存断言 | 见 §3.2 |
| 数字带口径 | 计数写明统计方法 | 见 §3.3 |

## 3. 三个必须写进规则的反例

### 3.1 「本地全绿」不等于仓库全绿

第一版资源核对断言「qrc 每条都在磁盘上，缺失 0 条」，本地通过，CI 的 port-policy 直接失败。
原因是 `.qm` 属构建产物（`.gitignore:15` 的 `*.qm`，`git ls-files resources/*.qm` 为 0），
本地那份是早前 `lrelease` 的残留。**那条断言当时测的是我的目录状态，不是仓库状态。**

规则化：**凡按文件存在性做核对，先问「干净检出会不会长成这样」**，并把检查拆成
「仓库必须提供」与「构建生成且可追溯到被跟踪源文件」两类。做法上再加一次显式模拟：
把 `.qm` 全部移走后复跑，确认结果不变。

### 3.2 从文档推断实现状态

我在 #28 上写过「文字省略仍未修」，依据是 D7 文档里「宽度比较被移除」这句话。
实际代码里 `common/lc_partselectionwidget.cpp:1405` 早在 D7 就设了
`setMinimumWidth(Widest + Overhead)`，且 `tst_localization.cpp` 的
`optionsMenuFitsItsLongestEntry` / `filterSubmenuFitsItsLongestEntry` 两条断言在宿主真实 PASS——
**缺的只是真机复验，不是修复**。已另发评论更正。

规则化：文档讲的是**断言的取舍**，不能用来推断**功能是否存在**。
「X 未实现」这类结论必须有代码位置或可运行的检查背书。

### 3.3 数字没有口径就不可复核

同一批引用先写 147、后写 145，差别来自是否剥离注释——不剥离时，我为解释缺陷写进代码注释的
`":/..."` 字样会把自己算成一个引用。

规则化：**任何计数都要写明统计方法**（含或不含注释、按文件还是按唯一串、修复前还是修复后），
否则读者无法复核，数字也就失去了意义。

## 4. 未复现的失败怎么写

本轮 `archive` 出现过一次 `12 passed / 1 failed`，此后 17 次本地采样与 Windows CI 产物（13/0）都未再现。
处理原则：**记为未解释的单点观测，不写成已定位或已修复，也不为它改生产代码**。
配套修掉的是取证工具本身——`scripts/dev/run-d3-tests.sh` 原先 `tee … | tail -3`，
而 QtTest 把 `FAIL!` 打在 `Totals` 之前，三行窗口恰好截掉失败用例名，同时循环开头的 `rm -rf` 删掉了
唯一结果副本。现在改为按 `^(FAIL!|QFATAL|Totals)` 回显并把结果复制到 `build/last-run/`。

**「套件报红但说不出哪一条红」不是证据**，与 D7 CI 侧 `*>` 产生 0 字节结果文件属同一类缺陷。

## 5. PR 描述该含什么

沿用 A / B 的 D8 文档结构，另加三项本轮证明必要的东西：

- **依据与机制分开**：宏关掉的是代码路径，菜单裁剪关掉的是用户可达入口，两层各写各的；
- **环境边界**：哪些结论只在宿主成立、哪些必须真机（字体、菜单宽度、打包产物权限）；
- **未决项**：未复现的失败、未关闭的 issue、仍待组长在产物上核对的声明。
