## 2. 清单：种子与闭包

### 2.1 两个数字的区别

| 概念 | 数量 | 含义 |
|---|---:|---|
| 种子零件（selection） | **1030** | 按分类预算直接挑选的顶层零件 |
| 最终顶层零件 | **1160** | 种子 + 依赖闭包引入的顶层零件 |

依赖闭包会引入种子未列出的顶层零件：某些种子零件引用其它顶层零件
（非 `s/`、非 `p/`），这些被引用者必须一并打包，否则用户会看到缺件模型。
因此最终 1160 > 种子 1030。

逐件清单见 **[`D2_零件清单.csv`](D2_零件清单.csv)**（1160 行，按 `origin` 列区分种子与闭包件）。

### 2.2 零件清单（CSV）

| 列 | 含义 |
|---|---|
| `part_id` | LDraw 零件 ID，不含 `.dat`，小写 |
| `origin` | `seed`（1030 行）或 `closure`（130 行） |
| `seed_category` | 种子所属分类（仅 `seed` 行有值，来自 `selection.txt` 的分组） |
| `panel_categories` | **运行时面板分类**：按 `DefaultCategories[]` 表达式匹配描述得出，`;` 分隔 |
| `category_count` | 匹配到的分类数（0 表示任何分类都不匹配，见下） |
| `introduced_by` | 闭包件由哪个零件直接引用（仅 `closure` 行有值） |
| `root_seed` | 该闭包件的依赖链上溯到哪个种子（仅 `closure` 行有值） |
| `description` | LDraw 官方描述 |
| `license` | `CC-BY-4.0` / `CC-BY-2.0+4.0` |

两列分类**故意分开**：

- `seed_category` 回答「这个零件为什么被选中」——预算表按分类分配；
- `panel_categories` 回答「装进库后它出现在面板的哪个分类下」——由
  `lcMatchCategory()` 对描述匹配决定，与预算表无关。

两者不能合并：面板分类由描述驱动，同一零件可能匹配多个分类，而预算只是一个
挑选配额。若只给一列，审核时无法判断"面板里 Brick 显示 156 件，但预算是 150"
这种正常偏差（闭包引入的零件同样会出现在分类树里）。

**覆盖率**：1160 件中 1156 件至少匹配一个分类；另有 4 件不匹配任何分类
（`30293`、`30294`、`62503`、`u9267`），它们是闭包件，描述以 `=` 或 `~` 开头
（别名/图元样式），在面板中不会出现在任何分类下，但作为被引用件必须随包分发。
`category_count` 列如实记录这一情况，不做填补。

### 2.3 依赖闭包的可复现校验

130 件闭包件的引入路径可逐条追溯（CSV 的 `introduced_by` / `root_seed`）：

```
顶层零件总数: 1160
种子: 1030
闭包引入: 130        ← 全部可达，无悬空
悬空引用: 0 / 1160
闭包深度分布: 1 层 81 件、2 层 41 件、3 层 4 件、4 层 4 件
```

遍历按加载器的解析顺序复现：先查 `mPieces`（顶层零件），再查图元表
（`parts/s/` 与 `p/`），与 `lcPiecesLibrary::FindPiece()` / `OpenArchive()` 的分流一致。
因此"闭包完整"等于"运行时不缺件"，不是另一种近似。

### 2.4 种子来源与可复现性

种子清单由脚本从 `DefaultCategories[]` 的 31 条表达式匹配官方库零件描述生成，
不手工挑选。生成规则见 D1 文档 §4.2（7 条原则）。

复核结果：

```
清单零件数: 1030
官方库中缺失: 0            ← 1030 个全部真实存在
官方库顶层零件总数: 24985
```

**无虚构条目**：每一个 ID 都能在官方库 `ldraw/parts/` 下找到。

### 2.6 为什么 Sticker 为 0

贴纸（Sticker）是装饰件，不属于建模核心闭环。D1 §4.2 的筛选原则已排除图案件，
Sticker 分类保留在树中但为空——用户不会看到"该分类有内容却打不开"的情况，
因为空分类在面板中不发请求。

若后续需要贴纸，应在预算表中给该分类单独配额，而不是放宽全局规则。

## 3. 分类：与源码的一致性

### 3.1 单一事实来源

分类树不是本方案定义的，而是来自 `common/lc_category.cpp` 的
`DefaultCategories[]`（格式 `"Name=表达式\n"`）。方案只是**按该表挑选零件**。

逐一比对结果：

```
源码分类数: 31
selection 分类数: 31
源码有但 selection 无: []
selection 有但源码无: []
```

**完全一致**，不存在"清单里有源码分类树里没有的分类"或反之的情况。
这保证了"装进库的零件"与"面板能显示的零件"不会脱节。

### 3.2 分类表达式语义（筛选依据）

| 记号 | 含义 | 例 |
|---|---|---|
| `^Name` | 整词匹配 | `^%Brick` 匹配 "Brick 2 x 4" |
| `^%Name` | 描述开头匹配 | 同上，更严格 |
| `\|` | 或 | `^%Boat \| ^%Sail` |
| `&` | 与 | — |
| `!` | 排除 | — |

筛选脚本按与 `lcMatchCategory()` 等价的语义实现，确保与运行时判断一致。

## 4. 资源部署方案

### 4.1 归档格式约束（由加载器决定，不可自由选择）

以下四条来自 `common/lc_library.cpp` 的实际代码，不是设计选择：

| 约束 | 代码依据 | 违反后果 |
|---|---|---|
| 根目录必须 `ldraw/` | `OpenArchive()` 对 `LDRAW/` 前缀 `memcmp`（:442） | **静默跳过**：条目被 `continue`，但仍返回成功 |
| `parts/`、`parts/s/`、`p/` | 名称大写后按目录前缀分流（:1389、:1392） | 零件找不到子件 |
| 必须含 `ldraw/ldconfig.ldr` | `LoadColors()` 优先从包内提取（:305） | **静默**回落内置色表，颜色显示错误 |
| 文件名大小写不敏感唯一 | 统一转大写后入 `std::map` | 同名冲突覆盖 |

#### 归档校验和回退说明（重要修正）

原稿把「根目录错误」写成「归档被当作无效」，这与加载器的实际行为不符。实际路径是：

```cpp
// common/lc_library.cpp:440-446  —— 根目录不对的条目被跳过，不中断
if (ZipFileType == lcZipFileType::Official)
{
    if (memcmp(Name, "LDRAW/", 6))
        continue;          // 跳过该条目
    Name += 6;
}
// ...
// :486
return true;               // 循环结束后无条件返回成功
```

`lc_library.cpp:256` 的 `Load()` 因此走成功分支，`lc_application.cpp:970` 也不会
走到「未找到零件库」的提示。**也就是说：根目录错误、或归档里根本没有零件，加载器仍返回
`true`，应用中表现为「零件库加载成功但零件数为 0」。**

> 补充：另一种失败路径（文件打不开、zip 头损坏）在 `:388` 返回 `false`，
> 此时 `Load()` 会回落 `OpenDirectory()` 尝试当目录加载，失败才返回 `false`。
> 两条路径的差别决定了校验不能只看返回值。

**结论：不能凭 `Load()` 的返回值判断零件库是否可用，也不能用它触发备用库。**
D3 必须在调用前后显式校验，四项缺一不可：

| 校验项 | 判据 | 不通过的后果（若不校验） |
|---|---|---|
| 目录结构 | 归档内**每个**条目都以 `ldraw/` 开头，无例外 | 全部条目被跳过，看似成功 |
| 关键文件 | `ldraw/ldconfig.ldr` 存在，且能解析出颜色条目 | 颜色静默错误 |
| 零件数量 | `mPieces.size()` 与本方案的 1160 相符（至少 ≥ 500，即需求下限） | 空库或残缺库上线 |
| 依赖完整性 | 零件的 `1` 行引用全部可解析 | 模型缺件，且不报错 |

第 4 项的实测口径：对全部 1160 个顶层零件做依赖闭包遍历，**悬空引用 0 个**。
不是抽样——每一件都走了。

备用库的触发条件应当用这四项的组合，而不是 `Load()` 返回值：

```
Load() 返回 true  且  四项校验全过   → 用精简库
Load() 返回 true  但  任一项失败     → 记录诊断，回退 resources/library.zip（128 件）
Load() 返回 false                    → 回退 resources/library.zip
```

这样即使精简库打包出错，也只是退化为 128 件，而不是「应用启动、面板空白、
用户以为零件库丢了」。具体的校验函数放在 `FindBundledLibraryArchive()` 之后、
`Application.Initialize()` 之前，属 D3 编码范围。

#### 本方案归档的实测校验结果

```
文件总数: 2741
顶层零件: 1160
子件: 669
图元: 911
ldconfig: ['ldraw/ldconfig.ldr']
非 ldraw/ 前缀: []        ← 无多余根目录（校验项 1 通过）
```

### 4.2 部署位置：三个候选路径

`FindBundledLibraryArchive()` 按顺序探测（D3 接入）：

| 顺序 | 位置 | 适用场景 | 优先级理由 |
|---:|---|---|---|
| 1 | 应用数据目录 | 首次启动把 zip 展开到可写目录 | 可热更新、可写 |
| 2 | `applicationDirPath()` | 桌面版随包分发 | 便于开发调试 |
| 3 | `:/assets/ldraw-lite/library-lite.zip` | qrc 内嵌 | 兜底，一定存在 |

**首发建议：qrc 内嵌（第 3 项）**，理由：

- 零件库与程序同版本，不会出现"库与程序不匹配"；
- 无需首次启动解压，无写权限依赖；
- 鸿蒙沙箱下应用私有目录的写权限路径更长，内嵌规避了该问题。

**风险**：3.7 MB 进 qrc 会增大 HAP 体积，且首次访问需解压到内存。
若真机首启耗时不可接受，改为第 1 项（首启展开到数据目录），
探测顺序已预留该分支，无需改调用方。

### 4.3 与现有资源的关系

当前 `leocad.qrc` 已含：

```xml
<file>resources/library.zip</file>      <!-- 内置 128 件，保留作兜底 -->
<file>resources/ldconfig.ldr</file>     <!-- 内置色表 -->
```

新增方案**不删除**这两个文件：

- `library.zip`（128 件）作为兜底：精简库**未通过 §4.1 的四项校验**时回退到它，
  保证应用仍能启动、面板仍有零件；
- `resources/ldconfig.ldr` 作为磁盘侧色表备用。

注意回退判据不是"加载返回失败"——见 §4.1「归档校验和回退说明」，
根目录错误的精简库同样返回成功，必须靠四项校验识别。

### 4.4 体积对照

| 方案 | 零件数 | 归档大小 | 说明 |

## 6. 精简 UI 草图（D2 第二项交付）

### 6.1 主窗口布局

```

│ 文件  编辑  视图  零件  子模型  帮助                          │  ← 6 个菜单，去掉打印/导出/渲染
├─────────────────────────────────────────────────────────────┤

├─────────────────────────────────────────────────────────────┤
│ 模型 │ 底盘 │ 车轮 │                                        │  ← 子模型标签栏（不可拖、不可关）
├──────────────────────────────────────────┬──────────────────┤
│                                          │ ┌──────────────┐ │
│                                          │ │ 零件 │ 颜色  │ │  ← dock 标签组
│                                          │ ├──────────────┤ │
│         模型视图（QOpenGLWidget）          │ │ 分类树       │ │
│                                          │ │ ┌──────────┐ │ │
│                                          │ │ │ 零件缩略图 │ │ │
│                                          │ │ └──────────┘ │ │
│                                          │ │ [搜索框]     │ │
│                                          │ └──────────────┘ │
├──────────────────────────────────────────┴──────────────────┤

└─────────────────────────────────────────────────────────────┘
```

要点：

- **保留子模型标签栏**——首版单工程，但 MPD 内的子模型仍要能查看与切换；
  标签栏**保留且可见**，只做三处收窄：不可拖动排序、不可关闭、不弹右键菜单（见 6.3）
- **右侧 dock 组**：零件 / 颜色 / 属性 / 时间轴 / 预览，默认显示"零件"
- **工具栏**：仅 Standard 常驻，Time/Tools 默认隐藏

标签栏与 §6.3 的「切换方式」是**同一套设计**：鼠标点标签是主路径，
`子模型` 菜单里的列表对话框是同一动作的第二个入口（名字多、标签栏放不下时用）。
两者都只切换当前编辑目标，不改 MPD 结构。

### 6.3 子模型切换：统一为一套设计

D1 结论：首版只开一个工程/文档，但**保留 MPD 内子模型的查看与切换**。

**先说明一处原稿的矛盾**：上一版 §6.1 写「标签栏隐藏」，§6.3 写「点击标签切换」，
两处自相矛盾。本节统一为一套设计，与 §6.1 的草图一致。

**选定方案：保留标签栏（可见），两个入口指向同一动作。**

理由：标签栏就是 MPD 子模型的唯一可视载体。隐藏它之后再想切换，用户只能靠菜单
深处的对话框去找，等于把最常用的导航藏了两层；而删掉切换能力又直接破坏 `.mpd`
的基础读写（D1 §1.3）。所以保留标签栏、只收窄它的**结构修改能力**。

| 项 | 首版处理 | 代码位置 |
|---|---|---|
| 标签栏 | **保留可见** | `QTabWidget` 在 `CreateWidgets()` 建好 |
| `setMovable()` | **关闭**（不能拖动排序） | `lc_mainwindow.cpp:89` 当前为 `true` |
| `setTabsClosable()` | **关闭**（不显示关闭按钮） | `:90` 当前为 `true` |
| 标签右键菜单 | **不注册**（`setContextMenuPolicy(NoContextMenu)`） | `:91` 的策略与 `:95` 的连接一并去掉 |
| 子模型**切换** | **保留**：点击标签，或在 `子模型 → 子模型列表…` 中双击 | `SetCurrentModelTab()`，`:1677`（`addTab` 在 `:1691`） |
| 子模型**列表对话框** | 裁剪后保留：隐藏新建/删除/重命名/导出/复制，关闭拖放排序 | `lc_modellistdialog` |
| 子模型**编辑**命令 | **移除**（`LC_MODEL_NEW`、内联、移动到模型等） | 见 D1 §3.2 |

即：**能看、能切，不能改结构。**

关于 `setTabsClosable(false)` 的一个细节：关掉关闭按钮后，`ModelTabClosed()` 仍挂在
`:94` 的 `tabCloseRequested` 上，但该信号在无关闭按钮时不会发出。**连接要不要保留**
不影响行为；首版选择一并断开，避免将来误以为还启用了关闭路径。

若后续要支持多工程（D1 已排除，非首版范围），才需要重新评估关闭语义：

```cpp
// common/lc_mainwindow.cpp:1073
void lcMainWindow::ModelTabClosed(int Index)
{
    if (mModelTabWidget->count() != 1)
        delete mModelTabWidget->widget(Index);
    else
        NewProject();     // 关掉最后一个标签 → 新建工程，不是空白状态
}
```

这段是 `setTabsClosable` 必须关掉的直接原因：关闭最后一个标签会**新建工程**，
而不是留下空窗口，对单工程首版是不安全的交互。

## 9. 复现方式

```bash
# 1. 取官方库（约 141 MB，不入库）
curl -A "leocad-harmony-library-fetch/1.0" \
     -o complete.zip https://library.ldraw.org/library/updates/complete.zip

# 2. 生成种子清单（从 DefaultCategories 匹配）
python3 scripts/library/generate_selection.py --library complete.zip

# 3. 解析依赖闭包并打包（固定时间戳，字节可复现）
python3 scripts/library/build_library.py --library complete.zip --output library-lite.zip

# 4. 六项校验
python3 scripts/library/verify_library.py --archive library-lite.zip --manifest manifest.json

# 5. 导出零件清单（D2 交付物，1160 行）
python3 scripts/library/export_part_list.py
```

第 5 步的输入全部来自前四步的产物（`selection.txt`、`manifest.json`、`library-lite.zip`），
不依赖网络，也不读官方完整库。因此清单可在任何拿到仓库的机器上重建并复核。若归档
缺件，该步直接报出「`<file>: unresolvable reference 'X'`」并以非零码退出，而不是
默默生成一份看起来正常的清单。

脚本在 D3 随代码一并提交。
