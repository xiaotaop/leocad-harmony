# 成员 C D9：测试矩阵

本文是 D9「完善测试矩阵」的交付物，也是首发前判断"改一处会不会顺手弄坏别处"的依据。

它回答三个问题：现在到底有哪些测试在跑、每个套件负责守住什么、以及哪些东西**没有**被自动覆盖（这一节比前两节长，是故意的）。

方案文档 D9 行给成员 C 的任务是「修复布局、字体、焦点、菜单状态；完善测试矩阵」。修复部分见 [MEMBER_C_D9.md](./MEMBER_C_D9.md)，本文只讲矩阵。

组长后续已完成一批 D9 新包真机回归，记录见 [D9_DEVICE_ACCEPTANCE.md](./D9_DEVICE_ACCEPTANCE.md)。本文的套件结果及 T-02 描述属于成员 C 交付时的宿主范围；真机新增通过项与仍未覆盖的字体、焦点、显示档位等项目以该验收记录逐项说明为准。

## 一、矩阵的两个入口

同一批用例，两个平台各一个入口：

| 平台 | 入口 | 状态 |
| --- | --- | --- |
| Linux / WSL | `scripts/dev/run-d3-tests.sh` | 本机实跑，见第三节 |
| Windows | `scripts/Run-D3Tests.ps1` | **本机无法执行**，只在 CI（windows-2022）验证 |

两个入口跑的是同一份套件列表和同一批 `.pro` 工程，但它们**不是**同一份实现，改动要同步两处（见第四节 T-01）。

不带参数跑全部套件，也可以只跑一个：

```bash
source .devtools/env.sh
bash scripts/dev/run-d3-tests.sh              # 全部 10 套
bash scripts/dev/run-d3-tests.sh menu         # 只跑菜单范围
```

## 二、10 个 QTest 套件

每一行都是"编译真代码、跑真逻辑"，不是静态文本检查。用例数是本轮实测的运行条数（`private slots` 加 `_data` 驱动的行数），不是源码里 `void` 的个数：

| 套件 | 工程 | 用例 | 守住什么 |
| --- | --- | --- | --- |
| `archive` | `d3-archive-tests.pro` | 13 | 坏归档必须被 `ValidateBundledLibraryArchive()` 拒绝——`Load()` 对"静默加载成空库"的归档返回 true，所以启动成功证明不了库是好的 |
| `priority` | `d3-priority-tests.pro` | 8 | 多库并存时选中**策展库**而不是内置 128 件库（P1 回归：`LoadPartsLibrary()` 在第一个成功的路径就返回） |
| `menu` | `d3-menu-tests.pro` | 11 | 首发菜单与工具栏范围：该删的删干净、该留的留下、不留空子菜单、不留空工具栏 |
| `modellist` | `d3-modellist-tests.pro` | 5 | 子模型列表对话框能切换、不能改结构（`LC_MODEL_LIST` 保留，但对话框直接调 Project 操作，绕过菜单） |
| `panel` | `d4-panel-tests.pro` | 15 | 零件面板的空态与坏库提示 |
| `preferences` | `d5-preferences-tests.pro` | 9 | 偏好设置的裁剪范围（19 个控件 + 6 个标签隐藏，该留的留） |
| `theme` | `d5-theme-tests.pro` | 14 | 主题切换后文字仍可读（D5-02 / issue #14） |
| `chain` | `d6-chain-tests.pro` | 9 | 零件面板真的能驱动建模链 |
| `localization` | `d7-localization-tests.pro` | 22 | 中文首发版读起来是中文，且**不改存储值**（分类/颜色名走显示层翻译） |
| `files` | `d7-files-tests.pro` | 9 | 授权保存路径 |

合计 **115 项，0 失败 0 跳过**（本轮实测，`EXIT=0`）。

D9 之前是 112 项：menu 套件因本次修复从 8 项增至 11 项，新增 `noVisibleEmptyToolbars`、`emptiedToolbarToggleIsNotOffered`、`toolbarsWithCommandsStayVisible`。

## 三、Python 静态检查

除了 QTest，还有若干 Python 检查脚本，由 `continuous.yml` 的 port-policy job 驱动。它们不编译代码，检查的是"文档承诺与仓库实际是否一致"这类只有读文件才能判断的事：

| 脚本 | 项数 | 检查内容 |
| --- | --- | --- |
| `test_network_scope.py` | 13 | 离线承诺：有没有代码路径会在首发版里发起网络请求 |
| `test_permission_scope.py` | 5 | 权限清单与发布文档是否一致（D10 新增，见下） |
| `test_packaged_resources.py` | 5 | 包内资源：`.qrc` 引用的文件是否都真实存在 |
| `test_export_part_list.py` | 8 | 零件清单导出 |
| `test_failure_log_retention.py` | 24 | 测试失败时是否留下证据（D9 从 13 项扩到 **24 项**） |
| `test_release_materials.py` | 4 | 发布材料冻结：图标哈希与 `docs/release/图标冻结.md` 一致、商店文案身份与 `CMakeLists.txt` 一致、不得重新引入 "or later" 解释、不得声称不存在的零件库重建脚本（D11 新增） |

合计 **56 项**。

`test_failure_log_retention.py` 补的是"构建失败"这条路径——原先 qmake/make 失败时输出写 `/dev/null`，失败现场什么都不剩。详见 [MEMBER_C_D9.md](./MEMBER_C_D9.md) 第二节。

`test_permission_scope.py` 是 D10 补的。它存在的原因是一次真实的漂移：发布文档写"除文件选择外不申请权限"，而打包产物实际声明了 6 项，其中 PRINT 对应一个首发版已经移除的打印对话框。上架要求权限逐项说明，这种不一致是阻断项，但**仓库里没有任何检查会注意到它**——`test_network_scope.py` 的文件头自己就写明"打包清单是否申请 INTERNET 由发布文档核对，不由本文件检查"。新脚本守三件事：记录产物里的每项权限都必须在文档里出现、产物不得出现 INTERNET、标为"建议移除"的行必须带理由。

它守的是**文档与留档产物之间**的一致性，不是文档与当晚打出来的包——仓库里没有构建、Qt 模板也没 vendor 进来。所以 RC0 解包核对清单仍是人工项。

## 四、没有被自动覆盖的部分

这一节是本文的重点。矩阵的价值不在于它覆盖了什么，而在于它**没覆盖什么**被写清楚了——否则下一个人会以为绿色就等于安全。

| 编号 | 缺口 | 现状 | 谁来兜 |
| --- | --- | --- | --- |
| T-01 | Windows 入口 `Run-D3Tests.ps1` 与 bash 入口不同源 | bash 侧 D9 已补构建失败留证；PowerShell 侧仍只写 `test-results.txt`，失败无独立留证 | CI windows-2022 |
| T-02 | 全部结论来自桌面（Linux/WSL + offscreen） | 没有一项在鸿蒙真机上跑过 | 组长真机验收（D8 §5 同例） |
| T-03 | 字体渲染 | offscreen 平台无真实字体栈，字体度量与回退路径**测不到** | 真机 + 人工目视 |
| T-04 | 焦点链 | offscreen 下没有真实焦点窗口，Tab 顺序只能验代码不能验体验 | 真机 |
| T-05 | 4 个渲染套件不在本矩阵内 | `tests/render-{context,shaders,framebuffer,readback}/` 走**独立 CMake + `render-context-ci.yml`**，不属成员 C 的 qmake 矩阵 | 成员 A |
| T-06 | `tests/input/`、`tests/model/` 同类 | 分别由 `member-a-input-tests.pro`、`member-b-tests.pro` 承载，入口不同 | 成员 A / B |
| T-07 | 新代码路径只用 stub 驱动 | 构建失败留证的三条路径由 stub qmake/make 驱动，未用真 qmake 跑过 | 首次真实构建失败时自然验证 |
| T-08 | 权限清单无自动校验（只能靠留档副本） | `test_permission_scope.py` 比对的是 `docs/evidence/leader/2026-11-02/...` 的**留档副本**，不是当晚的构建产物；仓库内无构建、Qt 模板未 vendor | 组长在 RC0 解包核对（issue #16 验收项） |

关于 T-03/T-04 需要说明一个容易误会的点：offscreen 平台下 `isVisible()` 对任何子控件都返回 false，因为窗口从未真正显示。所以在无窗口测试里判断"这个控件是否可见"必须用 `isHidden()`（它反映 `hide()` 是否被显式调用），不能用 `isVisible()`。D9 的工具栏用例就是这么写的，注释里也留了原因——这是踩过一次的坑，不是风格选择。

## 五、失败时留下什么

D9 修完后的行为（bash 入口）：

| 阶段 | 失败时留下的东西 |
| --- | --- |
| qmake 失败 | `build/last-failure/d3-<suite>-results.txt` + `...-build.log`，meta 里 `stage=qmake` |
| make 失败 | 同上，`stage=make` |
| 二进制未产出 | 同上，`stage=binary`（区分"不存在"与"存在但不可执行"） |
| 用例失败 | 同上，`stage=test`，result 里是真实失败清单 |

每次运行（无论成败）都会更新 `build/last-run/`。两个目录都是覆盖式，不是历史堆积。

## 六、维护方式

新增一个套件要改三处，漏一处就会"看起来加了测试但其实没跑"：

1. 写 `d<n>-<name>-tests.pro`（`include(leocad.pro)`，`SOURCES -= qt/qtmain.cpp`，`SOURCES += <用例文件>`）；
2. 把 `<name>` 加进 `run-d3-tests.sh` 的 `SUITES` 默认列表，以及 suite→project 的 `case`；
3. 把同样的东西加进 `Run-D3Tests.ps1`。

第 3 步最容易漏，因为改的人在 Linux 上，跑不到它。T-01 这个缺口就是这么来的。
