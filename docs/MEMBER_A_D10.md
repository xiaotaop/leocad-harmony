# 成员 A D10：渲染性能与缩略图加载

基线为 main `2c514fcbfffc8282ae53ffdbe20de62aed21f881`。组长在该版本的签名包上手工执行三轮同进程 LDR→MPD，均未再卡住。最后一轮有正常子模型缩略图。两个 PID 各有一次 `LEOCAD_THUMBNAIL_DEFERRED`，零件名乱码且状态为 `state 0 refs 0`。第一进程的两份日志包含同一个事件。原始记录见 [D9 组长真机 PR #55](https://github.com/xiaotaop/leocad-harmony/pull/55)。

## 加载与上传

- 最后一个使用者释放零件后，撤销等待队列中的任务和已排队的通知。进行中的加载保持零件有效，等工作线程完成后再清理。通过加载序号校验排队通知，避免旧事件在指针被回收或复用后交给缩略图。
- 主线程只将加载完成的网格打包上传。标记重建时，若当前网格已有有效缓冲偏移且总字节数与原缓存相同，继续使用原缓冲。有新网格或删除已缓存网格时继续重建。
- 视口用 FBO 编号、窗口尺寸和 DPR 直接判断状态是否变化。保持原有诊断内容，只在变化时构建 JSON。

两个受控回归验证了取消后等待队列和完成通知的路径。旧版在“完成后取消，再请求同一零件”收到 2 次通知，新版收到 1 次并生成非空缩略图。旧版在“工作线程暂未开始、取消并回收临时零件”仍发出 1 次通知，新版为 0。旧版两项测试进程都返回 1。这些用例重现了加载队列和通知缺陷。D9 乱码事件尚无法对应到具体零件或证明由同一路径导致，[#45](https://github.com/xiaotaop/leocad-harmony/issues/45) 继续作为 P1/Alpha 阻断跟踪。

## 渲染实测与规模边界

macOS ARM64、Qt 6.12 Release、正常模式、实际 DPR 2 和 2188×1396 framebuffer。真实 `QOpenGLWidget` 通过本地路径打开合成 MPD，含主模型、4 个子模型和 16 种库零件，实例数逐项断言。每个版本重复 3 次。首帧时间从已启动应用开始打开文件到测试视口首次 `frameSwapped`，包括文件加载和缩放适应。重绘样本从已设置相机的同步 `grabFramebuffer` 开始，包含读回，单位为毫秒。

| 零件实例 | 打开到首帧，旧版 → 新版 | 重开到首帧，旧版 → 新版 | 12 次重绘中位数，旧版 → 新版 |
| ---: | ---: | ---: | ---: |
| 500 | 39.1 → 41.9 | 42.5 → 51.5 | 6.4 → 8.5 |
| 2,000 | 47.0 → 38.9 | 62.5 → 69.7 | 10.0 → 10.6 |
| 5,000 | 71.9 → 88.5 | 97.4 → 90.7 | 19.8 → 15.9 |

表中每格是 3 轮的中位数。5,000 件另有一次重开到首帧约 429 ms。真实打开与重开的计时有波动，三轮数据未显示一致的首帧改善。每轮打开和重开仍各有一次正常模型上传。

在保留可见网格并重复标记缓冲重建的受控阶段，8 帧的上传从 **8 次降为 1 次**，每轮总传输由 **7,783,296 字节降为 972,912 字节**，每一帧都与阶段开始时的 framebuffer 一致。上述数字适用于该受控阶段。探针用 `LEOCAD_PERF_TRACE=1` 输出 `LEOCAD_GL_UPLOAD`，CPU 计时含缓冲打包和提交，不测 GPU 执行结束时间。零件实例数与唯一网格数是独立变量。

首发暂以 **2,000 个实例、16 种常用网格、4 个子模型**作为设备验收目标。先完成正常模式 30 分钟的编辑、窗口变化和保存重开，再确定鸿蒙首发的可发布规模建议。5,000 件是桌面压力点。更复杂的网格、纹理、显示档位和长期内存仍需设备样本。详见[真机交接](MEMBER_A_D10_DEVICE_HANDOFF.md)与[原始记录](evidence/member-a/2026-11-05/)。

- Mac 真实 Qt/GL 输入和视口回归，正常 DPR 1、1.5、2 与基础 DPR 2 每组 **47 通过、0 失败、0 跳过**。
