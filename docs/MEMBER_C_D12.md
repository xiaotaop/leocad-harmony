## 2. 复核发现的实质缺陷

不是校对错别字，是**三份材料之间真实的不一致**。

### P-1　6 项权限里 5 项完全没有 `reason`，唯一有的那项是模板串

按 2026-11-05 打包产物实测：

| 权限 | `reason` |
|---|---|
| `STORE_PERSISTENT_DATA` | 无 |
| `FILE_ACCESS_PERSIST` | 无 |
| `PREPARE_APP_TERMINATE` | 无 |
| `READ_PASTEBOARD` | `$string:qt_permission_reason_read_pasteboard`（Qt 模板串） |
| `GET_FILE_ICON` | 无 |
| `PRINT` | 无 |

权限说明 §4 原来只把 `READ_PASTEBOARD` 的 reason 列为待改，**没有指出另外 5 项根本没有 reason**。
读者会以为只有一处要处理。

已改：§1 表格新增「产物是否带 reason」列（6 行全部标出）；新增 §4.1 汇总缺口并给出中文文案草案；
§5 第 1 项补充说明「授权分级未查证**直接决定哪几项必须补**」。

**不越界的处理**：我没有替组长决定补哪几项。哪几项属 `user_grant` 需 reason、哪几项属
`system_grant` 不需要，本仓库无法判定（无 HarmonyOS 分级文档）。给 `system_grant` 项硬加 reason
反而会给审核留下"声明了不用的用途"的新问题。这条已写进未验证项。

### P-2　隐私政策全文不提权限

`grep '权限' docs/release/隐私政策.md` 原为**零命中**。隐私政策是提交给市场、也是用户真正会读的那份，
它的"不做什么"表里没有"申请哪些权限"。读者只能得出"这个应用不申请任何权限"的结论，而包实际声明 6 项。

已改：新增 §2.1「我们申请哪些权限」，6 项逐条写用途与"是否读取您的数据"，
明确不申请 INTERNET / GET_NETWORK_INFO，并把两项待移除权限的**已知不一致**如实写出。

### P-3　商店文案的权限表述不完整

原 §8 只写"不含网络权限"。包声明 6 项，市场审核读到的是"关于权限只有一句话"。

已改：改为"共 6 项、不含网络权限、逐项用途见权限说明 §1"，并列出 6 个权限名。

### P-4　零件库规模未标为子集

实测 `manifest.json` 的 `counts`：1160 件零件、669 子部件、911 图元、共 2741 文件。
文案原来只说"内置离线 LDraw 零件库"，不写"完整"是对的，但没有一处说明**这是精简子集**，
容易被读成完整官方库。

已改：详细描述补"1160 件精选零件（共 2741 个文件）……是完整 LDraw 官方库的精简子集，不是完整库"。

## 3. 新增的自动检查

`scripts/library/test_release_consistency.py`（5 项）：

| 检查 | 守什么 |
|---|---|
| 权限集合三向一致 | 权限说明 / 商店文案 / 隐私政策引用的权限名必须完全相同（排除明确"不申请"的 INTERNET 等） |
| 隐私政策须有权限节 | 防止该节被删回"不提权限"的旧状态 |
| 零件数与 manifest 相符 | 文案写 1160 就必须真是 1160；改清单不改文案会失败 |
| 禁用语 | "完整库""官方发布""已通过审核""已上架""官方授权"必须同行含否定，否则失败 |
| **截图标记完成须有文件** | 把 `[待拍]` 改成已完成，必须同时存在 `docs/evidence/leader/*d12*/` 下的图片，**防止只改状态不拍照** |

最后一项是本轮最该有的检查：截图我拍不了，但"没拍却标成拍了"必须失败。

**变异验证（4/4 捕获）**：删掉隐私政策权限节、改名一项权限、把零件数改成 1500、
把"不是完整库"改成"是完整库"/"本库为完整库"——全部非零退出，还原后通过。

> 过程中发现自己的第一版检查有漏洞：禁用语只匹配精确短语"完整 LDraw 库"，
> 把句子改成"是完整库"就能绕过。已改为匹配最短claim"完整库"，并对每种否定写法都生效。
